## 一、背景

2026-10-18 深夜的事故：`C:\Users\MaxNull\.dsh` 下的 `storages`、`profiles\ssid`、`sessions-ssid` 被外部整目录删除后：

1. 内核没有重启，内存里仍持有全部 storage 数据；
2. 一次 `memory_save` 触发了 dsh-memory 的写路径（**先 `reload()` 从磁盘重读 → 合并 → 全量写**），空磁盘让 `reload()` 得到空库，**内存里的 164 条 global 记忆被覆盖成 1 条**；
3. 当时 `memory.json` **没有任何一份存在于 `.dsh` 之外**——`storages-backup` 是空的，回收站里也没有。**没有恢复点**。

事故的直接原因是一次错误的写操作，但**损失的幅度由「备份缺位」决定**。project 层的 `memory_project_*.json` 因为有 `.bak-anchorfix` / `.polluted` 历史副本而幸存，global 层则完全裸奔。

## 二、决定

**在 `dsh-memory` 插件内做定时备份**，而不是依赖外部脚本：

| 决定 | 理由 |
|---|---|
| **目标目录在 `DSH_HOME` 之外**（默认 `~/.dsh-backups/memory/`） | 这次事故的直接教训：备份和原件在同一个目录树里，一次删除就一起没 |
| **只读复制**，绝不复用引擎的写入路径 | 写路径的 `reload()` 正是事故的放大器；备份不能走同一条路 |
| **按 `YYYYMMDD-HHmmss` 命名** | 可排序即时间序，保留策略不需要读文件内容 |
| **保留最近 N 份**（默认 14） | 无界增长会变成新的问题；14 份 ≈ 两周，足够覆盖「发现晚了」 |
| **失败只写日志** | 备份是附加能力，不能因为它不可写就挡住记忆读写与启动 |
| **默认启用** | 这是防护性默认；用户要关可以 `backup.enabled: false` |
| **关闭时补一次** | 定时器只在运行期间生效；`ctx.effect` 的清理函数里同步跑一次 `runMemoryBackup`，兜住关 DSH 前最后一段变更 |

配置面：`MemoryConfig.backup = { enabled, intervalMinutes, keep, targetRoot }`，缺省值见 README「定时备份」段。

## 三、边界（明确不做的事）

1. **只备份当前工作区的 project 文件**（`<cwd>/.dsh/storages/`）。多工作区的 project 记忆不在本机制范围内——插件拿不到其它工作区的路径，强行遍历会引入错误的假设。
2. **不备份会话日志**。`session.v4.jsonl.zstd` 是 append-only，不是全量重写 unit；它的问题（删了就是删了）不能用同一个机制解决。会话日志的备份归壳/外部脚本。
3. **不替代 SSiD 壳侧的 `backup-storages.mjs`**。两者互补：壳侧备份 `storages`（workspace 登记等），插件侧备份记忆文件；插件侧不依赖 SSiD 的计划任务，在任意 DSH 部署里都成立。
4. **不改动任何引擎写入逻辑**。备份只是文件系统层面的复制，记忆的读写路径与这次事故前完全一致。
