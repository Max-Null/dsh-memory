# 多实例写入协调：update 前先 select

> 状态：**已实现**（0.7.1）· 2026-09-17
> 关联：`seek-soul-in-darkness/docs/排查/2026-09-17-多实例共用storages.md`（上游根因与影响面）·
> DSH discussion [#6882](https://github.com/deepseek-ai/deepseek-harness/discussions/6882)（请上游做跨进程协调）

## 一、问题

DSH web 与 SSiD 桌面壳同时运行时共用同一个 `DSH_HOME`，两者的存储是同一批文件。DSH 的写入是「读—改—写**全量覆盖**」，且官方两个后端都声明不做跨进程协调：

- `storage-json`：「Rename is an atomic replace … **writer per process and last-write-wins is correct**」
- `storage-sqlite`：「No busy-wait or retry policy … **cross-process coordination is out of scope**」

于是另一个实例写入的记忆**只落在磁盘上**，被本实例内存态的下一整份写入冲掉——静默发生，没有任何提示。实测损失形态：工作区登记从 2026-08-22 起停止累积（142/235 个会话未登记），记忆同理。

## 二、方案

### 选定：写前重读（update 前先 select）

`reload()` 已存在（供外部编辑记忆文件后刷新）。冲突的本质是**内存态过期**——只要在开写前确认内存不比磁盘旧，就能消掉「覆盖对方改动」这个必然损失。

判据用存储文件的 **mtime + size**：与上次记录一致说明没人动过，变过才重载。代价是一次 `statSync`（磁盘没变时）。

### 备选与否决

| 方案 | 否决理由 |
|---|---|
| 换 sqlite 后端 | 同样声明跨进程 out of scope；且需 json→sqlite 迁移，转错即真丢 |
| 后端层加锁 | 锁只能罩住单次写入，而丢更新的窗口横跨「读—改—写」整个应用层周期 |
| 改 append-only 变更日志 | 存储格式变更，代价最大 |
| 启动检测只提示 | 知情但不解决丢失；可作为后续轻量补充 |

## 三、实现

五条不变量，违反任何一条都会退回原状、死锁或静默漏写：

1. **刷新后必须重新取表**——`reload()` 会 `closeAll()` 并重开 facility，刷新前拿到的 `table` 引用失效。
2. **刷新与读改写必须同处一个互斥区**——否则两个并发写会在两者之间穿插，刷新白做。
3. **不得嵌套**——`writeScope` 内部是串行链，嵌套即死锁。
4. **写入体内取表一律走 `projectTableFor`，不读同步缓存**——`reload()` 同时清空 `projectTables`；此后 `this.projectTables.get(cwd)` 拿到 `undefined`，工作区侧的写入被静默跳过（命中记账首当其冲：它只在内存态里记账，不报错也不落盘）。这条是复审时补的，见下节。
5. **重载要负责收尾**——它关掉的每一张已开的工作区表都得重新装回去。注入 provider 是同步回调、只读已打开的表，表被关掉就等同于「这个工作区没有常驻记忆」：工作区记忆会从上下文里静默消失，直到某次工具调用把它重新打开。这条是 0.7.2 补的——0.7.1 让重载从「面板上手动点一下」变成「每次发现外部写入就自动发生」，频率一上来，过去可以忽略的副作用就变成了常见现象。

落点（`src/engine.ts`）：

| 成员 | 职责 |
|---|---|
| `fileStamp` | 文件指纹 `mtime:size`；`missing` 表示文件不存在 |
| `globalStoreFile` / `projectStoreFile` | 存储文件路径（unit 文件名 = domain 名） |
| `noteStoreStamps` | 写入完成后记录指纹，作为「这就是我们造成的状态」的基准 |
| `refreshForWrite` | 写前新鲜度门：指纹不符即 `reload()` |
| `writeScope` | 一次写入的完整作用域：串行化 → 新鲜度门 → 执行 → 记指纹 |

改造方式是 **wrapper + inner**：公开方法只加一层 `writeScope` 调用，原方法体原样改名为 `*Inner`——每个方法只动签名行，避免整块缩进造成的大 diff。

覆盖的 9 个写入入口：`remember`、`update`、`setStatus`、`setInjected`、`forget`、命中记账 `markUsed`（含 `recordUse`）、三项启动维护 `migrateLegacy` / `demoteStale` / `verifyAnchors`。

**`recordUse` 不单独包**：它只被 `markUsed` 调用，重复进入 `writeScope` 会触发不变量 3。

### 生产实例验证（自 0.7.1 起，2026-09-17 晚）

上面的用例跑在临时目录 + 最小装配里，所以在真实运行的 SSiD（0.7.1）上又走了一遍完整冲突——**刻意不经过被测引擎的内存态**，直接用脚本改写 `~/.dsh/storages/memory.json`：

| 步骤 | 观察 |
|---|---|
| 备份 → 写一条临时记忆（33 条） | 基准 |
| 外部脚本：删掉那条临时记忆、新增一条标记记录 | 磁盘仍 33 条；指纹 `…5803.772:52399` → `…5810.722:52347`（mtime 与 size 都变了） |
| 引擎写一条新记忆（触发刷新门） | **外部新增的还在、外部删除的没被带回来、本地新写的落了盘、原有 32 条一条不少**（34 = 32 − 1 + 1 + 1，差集只有预期的那三条） |
| 清理 | 标记记录用 `memory_forget` 删除，复查无残留 |

**顺带把不变量 5 暴露了出来**：这一轮之后注入里只剩 global 记忆——重载清空了工作区表，而注入是同步读的。同一现象在凌晨的重启后也出现过一次，当时归因于「恢复的会话不再走 `session/created` 预热」，两者其实是同一件事的两面：**注入的工作区部分以「表已打开」为前提**。0.7.2 修掉了「重载后丢失」这一类；「重启后首轮」那一类仍在（见 CHANGELOG 的已知边界）。

### 复审时补掉的一处静默降级

不变量 4 不是设计出来的，是复审读代码时发现的：`markUsed`（命中记账）沿用了原始的**同步**取表 `this.projectTables.get(join(projectCwd))`，而其余 8 个写入入口都用了异步的 `projectTableFor`。差别只在重载之后——缓存被清空时，异步版会重开工作区存储（拿到磁盘上的最新数据），同步版直接读到 `undefined` 并跳过写入。后果是工作区记忆的命中计数偶尔不涨：不报错、不丢数据，只是「经常被翻出来」这条证据少记一次，而降级链条（自动升常驻 / 30 天淘汰）正是靠它驱动的。

两处值得写下来：

- **负向验证的第一次是假的**。第 5 例首版把工作区记忆写成了 global（漏传 `namespace: 'project'`），又在 global 存储文件不存在时就动手改它——用例确实红了，但红在 `ENOENT`，与被测行为无关；撤回「修复」再跑，红的还是 `ENOENT`。真正的失败信号是第二次跑出来的 `expected +0 to be 1`：**先证明「禁用修复时它必须因这条断言而红」，再读正向的绿**，否则绿的只是一个恰好不报错的场景。
- **「覆盖了所有写入入口」这类结论要按入口逐个数**。写成 wrapper + inner 时，前 8 个入口照抄同一个模板，第 9 个（`markUsed`）因为原实现读的是同步缓存而漏掉了——它长得像写入入口，但取表方式不同。

## 五、边界（不解决什么）

- **残余窗口**：两个实例在**同一瞬间**写时后写者赢。同时写**不同**记忆已不再互相影响。
- **指纹粒度**：mtime + size；同毫秒且同字节数的两次外部写入无法区分（概率极低，且下一次写入仍会重载）。
- **不覆盖工作区登记**：`workspace.json` 由 DSH 自己的 workspace 服务写，插件层够不着。它仍会被双实例互相覆盖，直到上游引入跨进程协调。现有的两道防线是轮转备份（`shell/scripts/backup-storages.mjs` + 计划任务）与那个 discussion。
- **临时同步会被回滚**：手工覆盖 `profiles/*/node_modules/@max-null/dsh-memory/` 只在下次 `pnpm install` 之前有效；长效部署要 npm 发版 + 更新三处版本 pin。
