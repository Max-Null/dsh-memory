# 决策：记忆之间的关系维度是否值得做（关键词共现分析）

> 日期：2026-09-19
> 状态：**已决 —— 不做**（数据否决）
> 触发：用户在网上看到一个记忆类应用的界面——全库记忆铺成一张图、节点间带 `INVOLVES` 连线——问「对我们的插件有什么可借鉴的」
> 关联：`docs/设计/2026-09-19-跨工作区可见性与分级索引-设计方案.md`（§3.3 索引行）、`docs/决策/2026-09-18-常驻注入判据.md`

## 一、问题

那个界面暴露了我们**结构上完全没有的一个维度**：记忆之间的关系。

- 我们的记忆是**孤立记录**：一条条存在表里，靠 `keywords` 的词汇重叠间接聚类，没有任何显式关联。
- 它把记忆连成网，且连线带语义标注（`INVOLVES`）。

值得追问的因此有三件事：图这个**形态**要不要学；`keywords` 共现能不能用来改**索引行的聚类**；以及能不能做**「搜到 A 带出 B」**。

## 二、数据（2026-09-19 全库实测）

对 `project` 与 `global` 两个存储里的 approved、非隔离、非模板记录做两两共现统计（复现见 §五）：

| 指标 | 读数 |
|---|---|
| 候选记忆 | 132 条 |
| 关键词密度 | 平均 **11.3** 个/条（最少 6、最多 24） |
| 共享 1 个关键词 | **273 对** |
| 共享 2 个 | 27 对 |
| 共享 ≥3 个 | 11 对 |
| 连通分量（以「共享 ≥2」为边） | **99 个** |
| **孤立点** | **86 个（65%）** |
| 参与成簇 | 46 条（35%） |

**簇的质量出奇地好**——三个最大的簇各自都是一个真主题：

| 规模 | 簇内高频词 | 主题 |
|---|---|---|
| 11 条 | `ssid(7)`、`profile(3)`、`隔离环境(3)`、`插件升级(3)` | SSiD 升级 / 部署 / 隔离 |
| 6 条 | `thresholdratio(3)`、`reasoning-chunks(3)`、`compaction(2)` | 上下文占用与压缩阈值 |
| 6 条 | `dsh-memory(5)`、`injected(3)`、`常驻注入(3)` | 记忆的注入机制 |

## 三、结论：三个候选都不做

### 3.1 图形态 —— 数据直接否决

把那张图画在我们的数据上：**132 个节点里 86 个是孤立散点**，其余 46 个挤成 13 个小簇（最大 11 条）。图的视觉语言暗示「万物互联」，而我们的真实数据是**散沙 + 几块石头**。形态与数据不符，画出来只会误导。

这是数据结论，不是审美偏好：换任何布局算法都改不了 65% 的孤立率。

### 3.2 索引行改用簇聚类 —— 增量配不上成本

现在 `indexNotice` 取词频 top-5，输出形如 `ssid(15)、dsh-memory(9)、quick-toolbar(6)…`；改用簇会输出 `ssid(7)、profile(3)、隔离环境(3)…`。

**两者都是「高频词 + 计数」，信息量没有实质差别**，只是后者的词更聚焦。为这点差别去改核心算法、重写相关测试、再走一轮发布部署（改三处 pin + 装实体 + 重启），不值。

### 3.3 「搜到 A 带出 B」—— 成本明显超过收益

只有 **38 对**记忆存在关联（共享 ≥2 词），意味着这个功能在 **71% 的搜索里什么都不会发生**，剩下 29% 里提供一条线索。

代价则是三样：检索返回结构要改、前端要呈现、**更要紧的是得设计「凭什么说它相关」的判据**——否则就是我们一直在防的静默混淆（见判据文档「不产生反馈的失败比摩擦更难发现」）。一条画错的关系不会报错，只会把人引向错误的联想。

## 四、数据确认了什么（正向收获）

这组数字**确认了一个此前只是直觉的设计前提**：**记忆是「一条一条的独立事实」，不是「一张关系网」**。

65% 的孤立率不是缺陷，是这类记忆的常态——每条记录对应一次具体的排查、一个具体的约定、一处具体的坑，它们本来就不该彼此纠缠。这正是我们选择「索引行报**规模与主题**」而不是「给记忆**建关系**」的原因。

反过来说：如果有人要做「记忆的图」，那更适合**笔记 / 知识库**（人工编织、天然成网），而不是**工作记忆**（事件驱动、天然离散）。

## 五、复现方法

```bash
node scripts/analyze-cooccurrence.mjs            # 只读分析，不写任何文件
node scripts/analyze-cooccurrence.mjs --min-shared 3   # 收紧门槛（默认 2）
```

共享 1 个词的 273 对是**噪声级**（凡是带 `dsh` 的都算），所以把「≥2」作为关联门槛。脚本支持调阈值，但改之前先看 273 : 27 这个比例——门槛降到 1 会让「关联」失去意义。

## 六、什么情况下重新评估

1. **孤立率显著下降**（例如跌破 50%）——说明记忆的形态变了（比如开始大量写「索引类」记忆）。判据：重跑脚本看孤立点占比。
2. **记忆量级跨过 500 条**——簇的绝对数会上去，「成片主题」在索引行里的价值随之上升。
3. **出现「一次检索要跨多条记忆」的真实场景**——那是需求侧信号，比数据侧指标更硬。
