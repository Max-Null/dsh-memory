# 协作假设（画像）派生视图 — 讨论稿

> 状态：**讨论稿**，未定稿。命名、选项与结论均待确认，不作为实现依据。
> 日期：2026-09-17 · 基线：dsh-memory 0.7.0 / dsh-habit 0.2.0
> 数据复现：`node scripts/measure-injection.mjs`（本文件所有数字由该脚本输出）

## 一、问题

常驻注入有硬上限（`src/injection.ts` 的 `DEFAULT_INJECTION_BUDGET`，默认 1500 字符），超预算按「最近使用优先」省略。候选池 = 所有 `approved + injected` 的记录，而 `approved` 池远大于预算能容纳的条数。

两条后果：

1. **溢出时被省略的是「最近没被搜到」的那条，不是「最不重要」的那条。** 一条每轮都该生效的长期约定，会输给一条上周刚被搜到的小坑。
2. **省略只出现在面板上，模型不知道自己少了什么。** 静默丢失，无法自我修正。

## 二、实测

| 项 | global | project | 合计 |
|---|---|---|---|
| 存储位置 | `~/.dsh/storages/memory.json` | `<workspace>/.dsh/storages/memory_project_*.json` | — |
| `approved` 条数 | 31 | 72 | **103** |
| 其中常驻 | 1 | 5 | **6** |
| 全部常驻所需字符 | 4,185 | 9,729 | **13,914** |

当前注入：候选 6 条 → 全部注入，**815 字符**，省略 **0** 条，预算利用率 **54.3%**，单条平均 136 字符，**每轮上限约 11 条**。

读法：

- **今天不紧张**：余 685 字符（约 5 条余量）。
- **临界点很近**：再升 5 条常驻即开始截断；而池子里有 103 条候选。
- **抬预算不是解法**：容纳全部候选需要 9.3 倍预算（13,914 字符），且池子仍在增长。
- **一个待验证的异常**：global 层 31 条只常驻 1 条。跨项目通用偏好本应是最该常驻的一类，实际几乎没升。可能是命中门槛（`AUTO_INJECT_HITS = 2`）与 global 记忆的检索机会偏少共同作用，需要单独验证再动结论。

## 三、选项

| 选项 | 做法 | 代价 |
|---|---|---|
| A 不做 | 接受溢出 | 溢出后模型静默丢失最重要的偏好 |
| B 抬预算 | 1500 → 3000/5000 | 每轮 token 线性上升，只推迟问题 |
| C 派生视图 | 从记忆归纳「协作假设」，带来源，独立开关 | 生成时机、失效机制、防漂移；错了会持续影响每一轮 |
| D 换择选策略 | 不按「最近使用」，改为人工钉住优先 + 余量按最近使用 | 需要定义「重要性」，可能引入新偏见 |

## 四、建议

**先做 D 的最小版本，再评估 C。**

1. D 不改数据结构，只换取舍规则，能直接消除「长期约定被小坑挤掉」这个具体缺陷。
2. 实测的 5 条余量为 D 争取了时间窗：等利用率长期高于 85% 再上 C。
3. C 的价值是**信息密度**（同样 1500 字符承载更多稳定信息），但它引入的新失败模式（锚定、静默过时）需要独立设计，不该与 D 混做。

## 五、若做 C：形态约束

- **派生**：随时可从记忆条目重新生成，不引入第二个事实源。
- **带来源**：每句标注 `[mem <id>]`，面板可点开核对。
- **重生成而非增量编辑**：源记忆变更即整体重算，避免逐条改出的漂移。
- **失效联动**：源记忆被删除或标 `stale`，对应行随之失效，不留无主陈述。
- **独立开关**：与记忆常驻开关分开，错了能单独关掉而不牺牲记忆层。

## 六、命名

建议叫**协作假设**而非「用户画像」。名字决定模型写出什么：叫画像，会写成无法验证的性格判断（「他是个注重细节的人」）；叫协作假设，会写成可操作、可核查的句子（「可机械检查的才进门禁，需判断的只写规范」）。描述的也是「在本工作区如何与他协作」，比断言他是什么样的人更诚实。

## 七、与既有设计的关系（2026-09-17 已定）

**助手中心不作为独立插件推进。** 它已停更、部分想法过时，其能力应当是 **dsh-memory 逐渐生长出的结果**——不引入横跨在记忆之外的第二个插件。

仍然成立的两条（来自 dsh-assistant-center v1.2 设计）：

- **人格模型（树干-分叉）**：persona = 树干（品种基因：方向与基调）；`assistant:<id>` 命名空间的 approved 记忆 = 分叉（个性）；长期记忆反哺人格表现（记忆决定人格）；稳定规律再蒸馏回 persona，人工门。
- **记忆层保持纯净**：「助手」是消费方的概念，不进记忆层。

于是本讨论的位置清楚了：**协作假设是这条演化路径的第一级台阶**，不是与助手中心并列的另一件事。单人格场景（当前工作区如何与用户协作）先跑通「从记忆派生一个视图」这条路；跑通之后，「每个 assistant 一个命名空间」只是同一机制的参数化。

待重估的是原设计里的执行模型、已定参数与参考实现分层（见记忆 `9ddf20b3` 的标注）。

## 八、边界：与 dsh-habit 的分工

`dsh-habit` 的闭环终点是 `dsh-memory.remember()`——它是**发现机制**（从纠正信号提炼新偏好），产出进记忆。协作假设是**读取端的聚合**。两者不重叠，也不该合并：把聚合塞进 habit 会让它同时承担发现与归纳两种职责。

## 九、反方（不做的理由）

- 记忆写入质量若继续提高，检索就够用，视图是多余的一层。
- 锚定是每轮生效的偏见，比「偶尔搜不到」更难发现。
- 面板已显示省略数，人工介入即可解决溢出（钉住重要的、删掉无用的）。

反方成立的前提是**有人定期看面板**。若实际不会看，溢出就是静默的——这一条可以用面板访问日志验证。

## 十、待决问题

1. 择选策略（D）是否改？改的话「人工钉住」之外还要不要别的优先级维度。
2. 若做 C：生成时机（会话启动 / 手动触发 / 记忆变更累积 N 条后）与生成者（当前会话模型 / 独立低成本模型）。
3. 协作假设是否参与 BM25 检索，还是只做注入。
4. 面板是否需要独立的「协作假设」页签。
5. global 层常驻偏少是机制问题还是数据问题。
6. 演化阶梯的下一级何时做：协作假设跑通后，`assistant:<id>` 命名空间的人格视图是同一机制的参数化，还是需要新的存储与作用域语义。

## 十一、社区同类方案（2026-09-17 调查）

[AI-Inner-Os](https://github.com/SummerSec/AI-Inner-Os)（支持 Claude Code / Codex / Cursor / Hermes / OpenClaw / OpenCode）已经实现了两件与本讨论重叠的事，其中有五条做法是我们没写进设计的。

**一、风格层与任务层分离**（`codex/AGENTS.md`）：人设只影响内心独白，**不影响主任务回复**。硬边界三条——主任务必须完成、独白不能替代实际交付、独白默认不长过主回答。这正是 §五 要的形态。

**二、`user-profile-distillation` 技能**（`skills/user-profile-distillation/SKILL.md`）就是本文档讨论的「协作假设」，且比我们的草案成熟：

| 它的做法 | 我们的草案 |
|---|---|
| **证据强度分级**：strong（多条重复）/ medium（出现几次）/ weak（可能但稀疏） | 缺 |
| **纠正优先**：用户的纠正比推断的模式证据更强 | 缺 |
| **隐私边界清单**：不推断受保护属性（种族/宗教/性取向/健康/残疾/政治/精确年龄）、不做心理诊断、不引用长片段、未经明确要求不写入文件/记忆/规则 | 缺 |
| **可见版本演进**：Profile v1 → v2，每次带变更日志；只做小增量，不整体重写 | 只说「重生成」，没定义版本可见性 |
| 默认 opt-in：不主动画像、不静默跨轮更新 | 缺 |
| 输出结构：数据范围 / 工作画像 / 沟通协作偏好 / 表达特征 / 协作建议 / 不确定性与边界 | 只有四行样例 |

**采纳建议**：把「证据强度分级」「纠正优先」「可见版本演进」「隐私边界清单」「默认 opt-in」五条补进 §五 的形态约束——它们正好填上那份草案的空白。这些是别人的实践结论，不是我们的推测。
