# 记忆的跨工作区可见性与分级索引：设计方案（2026-09-19）

> 状态：**设计待评审**（未实现）
> 关联：`docs/决策/2026-09-18-常驻注入判据.md`（§六 预算约束、§七 观察盲点）、`docs/设计/2026-09-18-常驻注入预算诊断-设计方案.md`（§六 未决 3「排序是否引入重要度」）
> 源码：`src/engine.ts`（表管理 / 路由）、`src/injection.ts`（渲染）、`src/index.ts`（注入 provider）

## 一、目标与非目标

**两个缺口，合起来是同一件事：不在场的记忆既看不见、也够不着。**

| 维度 | 现状 | 本方案 |
|---|---|---|
| **空间**（④） | 会话只能看见「当前 cwd 那一张表」，父目录与子目录的记忆**既不注入也不可检索** | 祖先链可检索；子项目以索引行可见 |
| **内容**（①） | 常驻预算外的记忆只有一行诊断，且它只覆盖「出局的常驻」，不覆盖从未常驻的绝大多数 | 在索引行里给出可寻址的规模与主题 |

**非目标**（明确排除，避免范围蔓延）：

- 不引入向量 / 语义检索——那是独立议题，判据见 `docs/决策/2026-09-18-语义检索通道启用判据.md`。
- **不自动删除任何记忆**。孤儿数据的处置是一次的、显式的、可回滚的操作（§3.4）。
- 不引入定时器或后台任务——索引行的生成沿用「组装时计算」这条既有路径。
- 不改 DSH 源码；不动 `workspace.json`（那是 DSH 自己的服务写的，插件层够不着）。

## 二、设计依据（2026-09-19 实测）

### 2.1 空间维度：136 条记忆，一个会话最多看得见其中一部分

全工作区扫描（2026-09-19）：

| 存储位置 | 条数 | 本会话（cwd = `WorkStation`）能读到 |
|---|---|---|
| `WorkStation/.dsh/storages/memory_project_3rf76j.json` | 101 | ✅ 就是它 |
| `seek-soul-in-darkness/.dsh/storages/memory_project_ubctph.json` | 1 | ❌ |
| `deepseek-harness/.dsh/storages/memory_project_34he9k.json` | 1 | ❌ |
| `deepseek-harness/.dsh/storages/memory_project.json` | 16 | ❌ 且永远打不开（§2.2） |
| `dsh-web-runtime/.dsh/storages/`（两份） | 17 | ❌ 且永远打不开（§2.2） |

**双向都断**：在 `WorkStation` 开会话读不到 `seek-soul-in-darkness` 的 1 条；反过来在 `seek-soul-in-darkness` 开会话，读不到 `WorkStation` 的 **101 条**。这不是「少读了几条」，而是**工作区层级在记忆层完全没有映射**。

### 2.2 一个必须先纠正的事实：那批记录不是「僵尸」，是「埋在旧命名文件里」

代码只打开 `memory_project_<djb2(cwd)>.json`（`engine.ts:474-479`、`:517-551`）。实测四个文件的真实身份：

| 文件 | 文件头 `unit.name` | 按哈希算出的期望名 | 结论 |
|---|---|---|---|
| `deepseek-harness/memory_project_34he9k.json` | `memory_project_34he9k` | `memory_project_34he9k` | ✅ 匹配，1 条**活的** `suggested` |
| `deepseek-harness/memory_project.json` | `memory_project` | `memory_project_ozipkv` | ❌ **代码不会打开它**，16 条读不到 |
| `dsh-web-runtime/memory_project.json` | `memory_project` | `memory_project_n20y2d` | ❌ 打不开；且与上一行**逐字节相同**（拷贝） |
| `dsh-web-runtime/memory_project_34he9k.json` | `memory_project_34he9k` | `memory_project_n20y2d` | ❌ 打不开；同样是拷贝 |

所以 34 条 `suggested` 的准确构成是 **1 条活的 + 33 条代码已不认识的旧文件**。它们没有「卡在等人工审核」——`migrateLegacy` 根本走不到它们，因为那份表从未被打开。

> **对 C 项的直接含义**：要做的是**把旧文件捞出来的迁移器**，而不是「给僵尸重新分类」。前提是先确认内容是否还有价值（§六 未决 3）。

### 2.3 一个实现约束：路径字符串形式决定哈希，正反斜杠不通

`projectBackendName` 对**传入的字符串**做 `toLowerCase()` + djb2，因此：

```
H:\MaxNull\WorkStation\seek-soul-in-darkness  → memory_project_ubctph   （实际文件名）
H:/MaxNull/WorkStation/seek-soul-in-darkness  → memory_project_6ta4jm   （算错）
```

现有代码靠 `join(projectCwd)` 统一成 Windows 原生分隔符来保证一致（`engine.ts:502` 的 `const key = join(projectCwd)`）。**祖先链实现必须复用同一个规范化入口**，否则算出的祖先文件名会静默不匹配——表现为「祖先明明有记忆，却什么都没找到」，且不报错。

排查提示：验证任何跨目录记忆问题时，先打印 `projectBackendName(join(cwd))` 与目录下实际文件名比对。

### 2.4 内容维度：诊断行已经是雏形索引，但它只覆盖出局者

0.9.1 的预算诊断行形如：

```text
（另有 16 条常驻因预算未注入：SSiD 插件更新:三段式、SSiD 部署与升级经验…）
```

它已经具备索引的两个关键性质：**列出不在场者** + **不占注入预算**。但它有三个边界：

1. 只列 `injected: true` 的出局者——**从未常驻的 100+ 条记忆不在其中**；
2. 上限 12 条，超出以 `…` 结尾；
3. 只报「有什么」，不报「一共多少、按什么去找」。

第 3 点正是「分级」要补的：告诉模型**规模和入口**，而不是把内容塞进来。

### 2.5 排序缺口：越稳定的约定越容易被挤掉

按 `lastUsedAt ?? updatedAt` 降序贪心（`injection.ts:68-69`）意味着**最近写的新记忆**会挤掉**很久没更新的长期约定**。实测已发生过：`1c19d2f8`（「DSH 源码只引用不改」，铁律级）曾因久未更新而排在末尾出局。

这与判据文档 §六 的结论一致——「两个方向指向同一个缺口：**排序里没有『重要度』这个维度**」。本方案**不引入重要度**（见 §六 未决 1），但要把它的证据面补齐：让「谁被挤掉了」和「库里还有什么」同时可见。

### 2.6 陌生环境下的自举：机制能建立，但提示词不自足

以「一台陌生机器第一次装上本插件」的视角复查（2026-09-19）。机制层的前提逐项成立：

| 前提 | 实测 |
|---|---|
| 存储目录不存在 | ✅ `storage-json` 会 `mkdir(root, { recursive: true, mode: 0o700 })` 自动创建 |
| 库是空的、无记忆 | ✅ `memory:recall` 返回空串，被 system-prompt 的 `.filter(section => section.text.length > 0)` 滤掉，不产生空注入块 |
| 自述与指引 | ✅ `memory:self` / `tool:memory` 是常量，任何环境都注入 |
| 工具 schema | ✅ 10 个工具全量注册，DSH 会把 schema 交给模型 |

**但提示词层有一个致命缺口：「该记 `global` 还是 `project`」全体系没有判据。** `memory_save` 的 namespace 参数说明只有一句 `Where it applies; defaults to global.`，GUIDANCE 与自述里均未提及分层判据。后果：陌生环境的模型会**全写 `global`**，`project` 层始终空着——而本方案的 ④-A / ④-B / ① **全部以「project 层有内容」为前提**，它们不会报错，只会**永远不触发**；README 宣称的「记忆跟随仓库分享、可 git 提交」同样默认不会发生。

**根因**：本机上的「好用」是**提示词与数月积累的记忆共同作用**的结果。namespace 该怎么分不在提示词里，而在既有记忆的实践里——提示词单独拿出来是不自足的。这属于「不产生反馈的失败比摩擦更难发现」的同一类问题（判据文档 §四）。

**推论（本方案的前提条件）**：④ 与 ① 必须与「提示词自足性修复」同版发布，否则在新环境里等于没做。修复项见 §五。

## 三、机制设计

### 3.1 祖先链解析（④-A）

**做法**：把「当前工作区的表」扩展为「工作区链的表集合」——从 cwd 起逐级向上，对每一级用 `projectBackendName(join(ancestor))` 算出候选文件名，**只收集文件已存在的层级**。

```text
cwd = H:\MaxNull\WorkStation\seek-soul-in-darkness
  自身   → memory_project_ubctph.json        存在 → 收
  上级   → memory_project_3rf76j.json        存在 → 收   （101 条）
  再上级 → memory_project_b9wpng.json        不存在 → 跳过
  盘根   → memory_project_3777kz.json        不存在 → 跳过
```

**为什么不用遍历目录找 `memory_project_*.json`**：哈希是确定性的，算出候选路径只需几次 `existsSync`；遍历目录既慢，也无法区分「这个文件属于哪一级」（哈希不可逆，只能正算不能反推）。

**范围与边界**：

| 决策 | 取值 | 理由 |
|---|---|---|
| 向上几层 | 到盘根为止，只收存在的层级 | 实测只有 2 级，成本可忽略；固定层数会漏掉深目录 |
| **读出**（`list` / `search`） | **纳入** | 这是本方案要解决的核心诉求 |
| **注入**（`memory:recall`） | 第一版不纳入；放开时**只纳入显式钉住的**（`injectedAuto !== true`） | 见下方「注入的分流判据」 |
| **写入 / 删除** | **只落当前 cwd** | 避免「这条写哪去了」；跨工作区写入是另一个议题 |

**注入的分流判据（第二版放开时的依据）**：常驻注入有两条来源，它们的**适用范围不同**——

| 来源 | 语义 | 跨工作区是否成立 |
|---|---|---|
| 自动升级（`injectedAuto === true`） | **统计推断**：「这条被本工作区的检索反复命中」 | ❌ 不成立——命中发生在哪个工作区，证据就只对那个工作区有效 |
| 显式钉住（`injectedAuto !== true`） | **有意决定**：「没人想起来搜也必须生效」 | ✅ 成立——规则不因会话换了个目录而失效 |

所以祖先链放开注入时**只纳入显式钉住的条目**。实测（2026-09-19）：`WorkStation` 表 104 条中 23 条常驻，其中只有 **2 条**是显式钉的（`010e9e96` embeddings 委托、`052e413c` 常驻注入判据），成本约 270 字符——在当前 1500 字符预算下装得下，不会挤爆子项目会话。

**为什么写入不动**：`memory_save` 写 project 时用的是会话 cwd，用户认知里「我在这个项目里记的东西」就该落在这个项目。让写入也能落到祖先会让「记忆去哪了」变成需要推理的问题——而这正是本方案想消除的那类不确定性。

**检索结果的来源标记**：结果里必须能看出这条来自哪一级，否则跨工作区召回会变成「记忆串味」。沿用现有 `[memory:<id>:<namespace>]` 形式，扩展为 `[memory:<id>:project@<相对路径>]`，例如 `project@上级` / `project@上级/seek-soul-in-darkness`。相对路径比绝对路径短，且让「离当前工作区多远」一眼可见。

### 3.2 邻居发现与目录行（④-B）

**做法**：注入里增加一行索引，告诉模型「子目录里还有什么」：

```text
（本工作区下另有 2 个子项目带记忆：deepseek-harness（17 条）、seek-soul-in-darkness（1 条）——用 memory_search 检索）
```

**关键约束：注入 provider 是同步的**（`SystemPrompt.context` 的 `text` 类型为 `string | ((context) => string)`，`index.ts:245`），而扫描目录是 IO。所以扫描必须放在**异步预热路径**（`ensureProjectOpen` 与既有的 `system-prompt/assemble` waterfall 补预热，`index.ts:261-273`），结果缓存进内存，供同步 provider 读取。

缓存键为 cwd；会话内扫描一次。实测 `WorkStation` 有 19 个直接子目录，其中 3 个带记忆文件——**只扫一层**即可覆盖当前所有实际情况，不递归。

**这一行与诊断行同类**：不占注入预算、自消除（没有子项目记忆时不出行）。它只报告「哪里还有」，不搬运内容——所以不会把子项目的记忆变成当前会话的持续成本。

### 3.3 索引行（①）

**结论先行：用户设想的「一条目录记忆」方向正确，但不该做成一条记忆。**

对比两条路径：

| | 做成常驻记忆 | 做成系统索引行（本方案） |
|---|---|---|
| 预算 | 占约 135 字符，且参与零和竞争、可能自己也被挤掉 | **不占预算**（与诊断行同待遇） |
| 维护 | 需要人工或模型在记忆增删后更新，**会腐化** | 每次组装时现算，**不可能腐化** |
| 失效模式 | 目录与内容不一致，且这种不一致无人察觉 | 无 |
| 可寻址 | 有 id 可 `memory_get` 全文 | 不需要——它的用途就是「告诉你去搜」 |

**索引行的内容**（拼在诊断行之后，同为不占预算的附加行）：

```text
（索引：本工作区另有 100 条记忆，主题集中在：SSiD 发版(14)、DSH 内核观察(12)、插件链路(11)、会话与工作区(9)、记忆系统(8)…）
```

**主题从哪来**：复用既有的 `keywords` 字段做词频统计（实测每条平均 10.0 个关键词、最少 6 个、0 条为空——数据基础足够）。取 top 5 主题，每个附条数，超出以 `…` 结尾。

**为什么按主题而不是按时间或 id**：检索是关键词驱动的，而关键词正是记忆写入时被要求"给多角度"的那个字段。主题索引与检索用的是同一套词汇，**索引里出现的词就是能搜到的词**——这是让索引真正可寻址的前提。

**限量**：索引行本身约 100–150 字符，不占预算但**必须是常数级**——主题数固定上限、条数只报数字，防止它随记忆增长而膨胀。

### 3.4 孤儿数据的一次性处置（④-C）

基于 §2.2 的纠正，这一步是**显式的考古动作**，不是常规迁移：

1. **先看内容再决定**：33 条躺在 `memory_project.json` 里的记录是 2026-08-16～08-19 的技术细节（会话日志修复、插件发布、上游讨论回复等），**大部分可能已无价值**。
2. **三个选项**（待用户拍板，见 §六 未决 3）：
   - **A 只读归档**：把旧文件移到 `storages/archive/`，不导入。零风险，保留可检索性（用 `memory_search` 的路径召回或直接读文件）。
   - **B 选择性导入**：人工过一遍，把仍有价值的迁到规范名文件（`memory_project_<hash>.json`）。
   - **C 直接清理**：确认无用后删除；`dsh-web-runtime` 下那份是逐字节拷贝，**可以无条件删**。
3. **不做自动迁移**：写一个「打开时自动捞旧文件」的迁移器风险不对等——旧文件里可能含已被判定为密钥/凭据的内容（`detectSensitive` 是 0.7.0 之后才有的），自动导入等于让它们绕过隔离检查直接进检索。

## 四、原则（供后续改动判断是否推翻）

1. **可发现优先于可携带**：索引只报告「有什么、在哪、多少」，不搬运内容。每轮成本恒为常数。
2. **注入与检索分级**：祖先记忆第一版**只进检索不进注入**。要放宽必须给出「为什么这条祖先记忆对子项目会话也必须每轮在场」的理由。
3. **写入位置不猜**：写与删永远只落当前 cwd。
4. **不自动删除**：孤儿数据的处置是显式动作，且默认选项是「保留」。
5. **复用排序，不发明排序**：本方案不改 `renderInjection` 的取舍规则（§六 未决 1 是独立议题）。

## 五、第一版范围（最小可验证集）

**④-A 祖先链（检索侧）**

- `engine.ts` 新增祖先链解析（复用 `join(cwd)` 规范化，禁止自造路径形式）
- `allRecords` / `search` 的表集合从单表扩为链；结果带 `project@<相对路径>` 来源标记
- **注入路径不动**（`recallRecords` 保持只读当前 cwd）
- 测试：链上多级命中、同名记忆跨级不串味、无祖先时行为与现状逐字一致、正反斜杠路径形式不产生假阴性

**④-B 目录行**

- `ensureProjectOpen` 路径上做一次子目录扫描（一层），结果缓存
- `recallText` 追加邻居索引行（无邻居时为空串）
- 测试：无子项目记忆时不出行；有则行内含项目名与条数；扫描结果被缓存（第二次组装不重复 IO）

**① 索引行**

- `injection.ts` 新增主题聚合纯函数（输入全库记录，输出 top-5 主题与条数）
- `recallText` 追加索引行（常数级长度上限）
- 测试：空库不出行；主题按词频降序；条数正确；长度不随库增长（构造 1000 条记录断言行长恒定）

**④-C 孤儿处置**

- 先只做**清点与报告**：新增一个只读诊断（脚本或面板项）报出「哪些文件当前代码打不开」
- 实际处置（归档 / 导入 / 删除）等用户在 §六 未决 3 拍板后单独执行

**提示词自足性（④/① 的前置，与它们同版发布）**

- GUIDANCE 补 namespace 判据：**「换个项目，这条还成立吗？」** 成立 → `global`；不成立 → `project`
- 自述修正工具清单（6 → 10，补 `prompt_*` 系列）、补两层记忆说明与 `memory_confirm` 用途
- 理由见 §2.6：这一步不做，④ 与 ① 在新环境里等于没做
- 测试：断言运行时渲染的 GUIDANCE 含判据问句、自述含全部 10 个工具名

**明确不做**：重要度排序、向量检索、跨工作区写入、自动删除、递归扫描子目录。

## 六、未决

4. **邻居扫描要不要递归**。当前实测只扫一层就覆盖全部情况（3/19 个子目录带记忆）。若将来出现「孙目录才有记忆」的场景再评估；递归的成本与不确定性都不值得提前支付。

5. **来源标记的形式**。`project@上级` 是相对路径，读起来短；但若会话 cwd 很深，相对路径可能比绝对路径更长。是否需要按深度切换表示法，待实现后看实际注入文本长度再定。

6. **写路径的新鲜度门要不要覆盖祖先链**（2026-09-19 实测发现）。`refreshForWrite()` 比对的清单是 `[globalStoreFile(), projectStoreFile(projectCwd)]`——**只有 global 与当前 cwd 两个**（`src/engine.ts:790-791`）；而同一套协调里 `noteStoreStamps()` 记的却是 **`projectTables.keys()` 的全部已打开表 + 当前 cwd**（`:770-779`）。**记录与比对不对称**：某个祖先层一旦被会话打开过，它的指纹被记下了，却从来不被检查。后果是外部（另一实例、或工具直接改文件）动过该层之后，门看不见 → 不 `reload()` → 用内存里的旧表读改写 → **整份覆盖**磁盘。

   实测（2026-09-19，受控探针）：在祖先层 `H:\MaxNull\.dsh\storages\` seed 一条探针，而该层此前已被本会话缓存过 → 搜新 token **返回空**；磁盘上的文件被换回**早已删除**的旧记录，且 `hitCount` 由 1 涨到 2，新写的探针被抹掉。

7. **记忆的版本历史（「学 git」）**（2026-09-19 提出）。动机**不是防覆盖，而是可追溯**：本插件的核心设计是**静默生效**（写入即 `approved`，没有人事前点头的机会），那「事后能查」就不是锦上添花，而是这套设计的必要配套——而现在一条记忆被 `update`、被 30 天规则自动撤下常驻、被隔离、被 `forget`，**全都不留痕**。

   **它和未决 6 不是一回事**：那个是**防止**丢失更新（收窄窗口），这个是丢了**能找回**（窗口还在，但不再是永久损失）。互补，不能互相替代。

   **一个术语上的提醒**：git 存的**不是 diff**，是**快照**（每个 commit 一棵完整的树），diff 是查看时按需算出来的。对记忆这个规模（实测 108 条 / 212 KB）快照完全负担得起，不必上内容寻址 + packfile——要学的是它的**语义**（不可变版本、父指针、可追溯），不是它的存储技巧。

   **最小形态（分三步）**：

   - ✅ **第一步（2026-09-19 已做）**：把工作区记忆纳入 `backup-storages.mjs` 的每小时轮转快照。在此之前，连**粗粒度**的整库备份都不覆盖它们——备份扫的是 `~/.dsh/storages/`，而 project 记忆在 `<工作区>/.dsh/storages/`（改后 21 个文件 / 404 KB，含 6 份工作区记忆）。
   - ⏳ **第二步**：**旁路**追加式历史——主文件仍是「当前状态」，写入路径不动；另开 append-only 的 `<hash>.history.jsonl`，每次写入追加一条 `{时间, 记忆id, 操作, 改动前, 改动后}`。旁路的含义是：它坏掉也不影响主流程。
   - ⏳ **第三步**：查询入口（如 `memory_history(id)`）——否则记了没人看，等于白记（判据：工具必须带描述、能被未来的会话发现）。

   **待验证的前提**：多进程同时 append 同一个 `.jsonl` 的**原子性没有验证过**——长行会不会交错损坏需要实测，不能假设。若不可靠，备选是每个实例写自己的历史文件，或让历史写入也走 `writeScope` 那把锁。

   **待定**：保留策略（按条数还是按时间轮转）；以及历史要不要进检索（倾向**不进**——它是审计材料，不是记忆内容，不该占每轮成本）。

8. **提升通道（`memory_promote`）要不要现在做**（2026-09-19 提出；用户当日决定：**先记设计，不做**）。**问题**：委托把「这条记忆该留在本工作区、还是提升到祖先层 / global」的判断权交给了模型，但 `memory_save` 的目标层由 `execProjectCwd(exec)` 决定、**参数里没有指定层的东西**（`src/index.ts:335-345`）——模型能写【当前 cwd】和【global】，**写不到祖先层**。于是判据里最需要工具的那一条（「对兄弟工作区也成立 → 提到共同父目录」）**判得出、做不到**。

   **没有工具时的歪路**：程序化写祖先层文件是可行的（`scripts/ancestor-probe.mjs` 正是这么造探针的），但它**绕过 `writeScope` 的串行区**，还得自己算 djb2、造 unit/tables 结构——易错，且踩在未决 6 刚修好的那条缝上。**一个不存在的工具比一个不完美的工具危险。**

   **设计（若做）**：独立工具 `memory_promote(id, to)`，**不动 `memory_save` 的语义**（保住 §3.1 那条「写入只落 cwd」——它是用来消除「记忆去哪了」这类不确定性的）。三条约束：

   1. **不做自动化**——只提供「模型明确判断后调用」的能力，**不搞**「命中 N 次自动提升」。提升是广播动作，自动化会制造正是 §3.1 想消除的那类不确定性。
   2. **`to` 只取祖先链上的层（含自身）或 global**——可向上提、可移回自身，**绝不横向、绝不往下**。
   3. **移动而非复制**——继承是单向向上的：把一条记忆从子目录挪到父目录，子目录**仍然看得到它**，所以移动不会让任何原本能看见它的会话失明。（这条论证在「往下」或「横向」时失效，那正是约束 2 的理由。）

   **判据**（由模型执行）：只对本项目成立 → 不动；对兄弟工作区成立 → 提到**共同父目录**（不是 global）；对所有项目成立 → 才进 global。出手前问一句「放到这一层之后，**哪些工作区会看到它**」——名单里若出现毫不相干的项目，就是放高了。**保守优先：提升是广播，放错的代价高于不提升。**

   **时机**：技术前提已具备（未决 6 的修复让程序化写祖先层会被 `reload()` 感知，而不是被静默覆盖）。**当前真实需求接近于零**——子项目记忆共 2 条，且都只属于本项目。所以这一票投的是**通道的完整性**，不是眼下的便利。

   **待续**：第一次真实需要提升时再做。在那之前——**需要提升时不许手动改文件，必须先把工具补上**。

**实测场景（2026-09-19，本机）**：孤儿分布在 `WorkStation`（`memory_project_memory_project_3rf76j.json`，双重前缀旧名，1 条）、`deepseek-harness`（`memory_project.json`，无哈希后缀，16 条）、`dsh-web-runtime`（同两份的拷贝，17 条）。三处 `project` 存储里只有 3 个文件是当前代码认得的。

**实现要点（供后续改动参考）**：

- 祖先链只做 `existsSync` 判定（哈希是确定性的，不需要遍历目录），且**只收已存在的层级**——对不存在的层级打开表会让 `JsonStorageBackend` 凭空创建空文件。
- 定位类操作（`update` / `forget` / `setStatus` / `setInjected` / 命中记账）统一走 `locateRecord`，语义是「global 优先，其次自身 → 祖先」。**检索得到就要改得动**，否则「找得到却删不掉」是最别扭的一种不一致。
- `markUsed` 也必须跨链：祖先记录被跨区命中却不记账，它们的 `lastUsedAt` 会长期不动，被 30 天规则误撤。
- 注入路径（`recallRecords`）**保持只读当前 cwd**——这是设计决定，不是遗漏（§3.1）。
- 两个同步读取口（`neighborsOf` / `indexCandidates`）都只读**已打开/已缓存**的表：注入 provider 是同步回调，这是它唯一能做的事；未预热时该轮相应行缺席、下一轮补上。
- **已知缺口（§六 未决 6）**：写路径的新鲜度门 `refreshForWrite()` 只比 global + 当前 cwd，**不含祖先层**——而同一套协调的 `noteStoreStamps()` 记的却是全部已打开表。记录与比对不对称，后果是「被缓存过的祖先层若遭外部改动，会被内存态静默覆盖」。这是 ④-A **只扩了读、没扩写**的残余。
