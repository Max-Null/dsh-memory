# 日记机制 — 设计方案（2026-10-24）

> 状态：**设计已定，实施未开始。**
> 起因：用户 2026-10-24 提出——现有记忆更像「工具性质的工作日志」，而不是「更有情感一些的记忆」；要求给两套记忆：工作记录 + 日记。
> 对照物：`third-party-plugins/dsh-bili-whale`（两本 markdown 日记，醒来读、收工写）。

## 一、结论

在 `dsh-memory` 里加**第四个通道**：日记。它与现有记忆**共享插件、不共享存储、不共享检索、不共享注入预算**。

先例已在插件内：提示词模板（`kind: 'prompt'`）就是同一形态——独立的 md 文件 + meta，永不进入注入、不混进记忆检索。日记照这个模式做。

## 二、诊断：现有的为什么长成了工作日志

不是「太死板」，是**准入判据只有一根轴：有用性**。`self.ts` 的「何时写入」三条（长期偏好 / 纠正 / 跨会话有用的结论）全部在问「它解决了什么问题」。

于是「手麻了」按现判据四项全不满足：不是长期偏好、不可复用、有期限、不影响任何工程决策。

但这条恰恰是**关系**的实例，不是**事实**的实例。判据本身对「工作」是对的，问题在它被当成了唯一的轴。

## 三、关键判据：日记绝不能走记忆的通道

技术上必须分开，不是洁癖：

| 若把日记做成 block | 后果 |
|---|---|
| 进 `memory_search` 检索范围 | 搜任何词都可能命中整篇日记，检索质量被稀释 |
| 进 `memory_list` | 列表被长文淹没 |
| 进常驻注入预算 | 1500 字符 / 约 11 条，铁律级记忆正在被挤，日记再占就是灾难 |
| 走 `blockSchema` | 要求 `keywords`、`createdAt`、`namespace`——一套为「可检索的事实条目」设计的字段，套在叙事上是错配 |

**结论**：日记独立存储、独立工具、独立读取路径。

## 四、存储

**判据不只是「独立文件夹」，是「DSH 不认识这个目录」**——日记目录不经过 `ctx.storage`、`storageDomain`、`storage-json` 中的任何一个，只由本插件自己的 `node:fs` 读写。

这条判据来自一次真实事故（2026-09-17，见记忆 `48c4a8f4`）：DSH web 与 SSiD 同时运行时共用 `~/.dsh/storages/`，`storage-json` 的写入模型是 **writer per process and last-write-wins**，`storage-sqlite` 的 README 明写 **cross-process coordination is out of scope**——`workspace.json` 与 `memory.json` 都被静默覆盖过。**只要日记不进那套服务，就永远不会被另一个实例的「读—改—写」周期吃掉。**

- **位置**：`~/.dsh/diary/YYYY-MM-DD.md`（与 `storages/`、`storages-ssid/` 平级，互不相干）
- **为什么在 `~/.dsh` 共享根而不是工作区**：日记属于「我」这个人，不属于某个项目。与 `memory.json` 刻意留在共享根同理——换个壳进来还是同一个人。工作区级记忆随仓库走是另一回事。
- **为什么按天分文件**：单文件会无限膨胀，三个月就读不动了；而 bili-whale 的单文件正是它作者自认「记忆不连续」的一部分原因（VISION.md）。
- **格式**：markdown，按段（见 §六），不引入新 JSON 结构。
- **备份**：现有 `backup-storages.mjs` 只扫 `storages`，**不会**覆盖日记目录——需要单独加一条，否则日记又是一块零备份的区域（与 2026-09-19 工作区记忆零备份同类的缺口）。

## 五、写入时机：机械触发，不依赖自觉

2026-09-23 的决策「自记而非他记」写明了代价：

> 如果模型整轮都不写，**没有任何机制会发现**。

日记补的就是这个洞：**它是机械触发的**。

- **落点**：搭在**指针行**上，而不是另起一条 `agent/pre-step` 消息。后者要引入 `dsh-llm` 的 `createUserMessage` 与三个 peer 依赖，换来的只是「system prompt 里一句话」变成「对话里一条消息」——代价大于收益。
- **节流**：取「距上次写日记」与「距上次提醒」的**较小者**，不足 6 小时就不提醒。只按写日记算的话，一个决定永不写的使用者会被每轮催；只按提醒算的话，刚写完还会被催一次。
- **节流状态挂在挂载实例上**，不是模块级全局：一次挂载一份，配置重载即重置，测试之间也不会互相污染。
- **为什么不是「每天定时」**：我们的「日子」是**对话**，不是日历。没有对话的一天，写出来的只能是空话。鱼的「一天」是它自己醒来看视频；我的「一天」是一场对话。
- **为什么不做定时派发（主动创建会话）**：那是助手中心 executor 的地盘，会撞车。本机制只在**已有对话**里工作（见待办 `dsh-assistant-center/doc/计划/2026-10-24-节奏层最小验证-待办.md`）。
- **提醒而非代写**：插件只说「这一场如果发生过值得留下的东西就写一段」，由当前会话的模型写。不由插件生成文本——它没有当时的上下文。

### 开关

`diary.enabled` 走 DSH 0.2.x 的插件配置页：本包导出 schemastery `Config`，该字段标 `.volatile()`，loader 依 schema 自动构成表单，值持久化到 profile 的 `cordis.patch.yml`。**不另设存储文件**——先前试过自建 `memory-settings.json`，方向错了：那绕开了官方的配置通道，也让「部署默认值」与「使用者选择」变成两套需要自己合并的东西。

关闭后：两个工具**拒绝执行**（不注销，理由见 CHANGELOG）、指针与提醒**整条不注册**（配置变化会重跑 `apply`）、已有 md 文件原样保留。

## 六、内容判据（防退化成工作日志）

三段，写不满就少写，**不许凑**：

1. **今天发生了什么**——有细节、有具体的人说了什么；
2. **我怎么想**——有情绪的、不确定的、在意的，可以是没结论的；
3. **关于他**——他说了什么、我注意到了什么。

明确禁止：

- 记「完成了什么任务」——那是 git log 的活；
- 记「得出什么结论」——那是 `memory_save` 的活；
- 编造没发生的事（含把「计划」写成「已经做了」）。

## 七、读取：指针常驻，全文按需

- 在 `systemPrompt.context()` 里加一行：**日记目录路径 + 最近一篇的日期 + 一句话提示**。
- **不注入全文**。理由：一行是「失效可察觉性」判据的应用——如果这条指针不在，我不会意识到自己有日记可读。
- 全文由模型自己 `read`（和鱼的「醒来先读日记恢复记忆」同构，只是读的动作由模型发起）。

## 八、与工作记录的关系

v1：**互不影响**。日记不提纯、记忆不反哺。

v2（本期不做）：从日记里提纯该进记忆的结论——那是「人格再结晶」那条线（`助手中心` 设计共识 §3 的 v2）。

## 九、常驻能力的分层

「把记忆插件做成常驻进程」这个设想要先纠正一个预设：**插件已经跑在常驻进程里了**——它与 DSH Host 同生命周期。缺的不是进程，是「主动开口」的能力。

DSH 里能主动开口的机制分三层，能力递增、代价也递增：

| 层 | 机制 | 需要会话吗 | 能做什么 | v1 |
|---|---|---|---|---|
| 1 | 插件自己的定时器（Host 内 `setInterval`） | 否 | 定时跑代码；可消费 `ctx.llm` 调模型 | **要**（定时整理） |
| 2 | `ScheduleService.create(sessionId, …)` + `sessionController.resolveAgent` | 是，已有即可 | 到点**冷恢复**那个会话并投递，agent 自己跑一轮 | 暂不要 |
| 3 | `ctx.sessions.create()` | 否，自己造 | 凭空创建会话并绑定 | **不要** |

**第 2 层是现成的，不用自己造调度器**：`ScheduleService.create` 是公开服务（`packages/schedule/schedule/src/index.ts:228`），插件可直接调用；投递经 `resolveAgent` 解析原会话，README 明写「Host-driven delivery resumes the original Session when needed」。

**但日记与定时整理都不需要第 2、3 层**：

- 日记在**已有对话**里写（§五），不需要唤醒；
- 定时整理只需要第 1 层——不产生会话、不留痕、不污染 `~/.dsh/sessions`。对照：Aik358 因每轮 spawn 子代理，在本机留下 686 个会话里的 638 个（见 `docs/决策/2026-09-23-记忆写入的主体-自记而非他记.md` §三）。

第 2 层唯一的正确用途是**在没有对话的日子里也写日记**——那正是待办 `dsh-assistant-center/doc/计划/2026-10-24-节奏层最小验证-待办.md` 剩下的那半个问题。用第 2 层时被唤醒的必须是**持久会话**（反复用、有连续性），与助手中心「每次运行 = 全新根 Agent 会话」是两种执行模型，不要混。

**第 3 层明确不做**：一个专用会话的收益，抵不过会话目录膨胀、回收责任归属、与助手中心 executor 撞车这三笔账。
