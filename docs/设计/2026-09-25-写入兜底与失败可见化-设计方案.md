## 一、背景：一次真实故障

2026-09-25 实测。一条记忆被写入 `anchor: { kind: "path-exists", name: "<绝对路径>", value: "present" }`：

- **写入当场成功**——`memory_save` / `memory_update` 都不跑存储 schema 校验；
- 用户重启内核后，**该工作区 154 条 project 记忆全部不可见**：注入索引从 184 条掉到 30 条，
  `memory_list({ namespace: "project" })` 返回 `[]`，`memory_search` 只出 global 结果；
- **数据一条没丢**——文件里 `tables.blocks` 有 154 条、`unit.name` 正确。丢的是**可读性**。

**故障链条**：`engine.create()` 把 `input.anchor` 原样塞进 block（`dist/engine.js:702`）→ `table.put(id, block)`
直写（同文件 `:707`）→ 写入路径不校验 → 下次打开 domain 时 `dsh-storage-domain` 逐条 zod 校验
（`lib/index.js:371`）→ 一条不合格即抛 `invalid-record`（同文件 `:424`）→ **整个 domain 打不开** →
上层 `catch(() => undefined)` 吞掉（`engine.js:352` / `:425` / `:483`）→ **静默失联**。

判据：**写入放行、加载才炸、失败还被吞**——三层里任何一层立住，都不会出现「用户重启后才发现半个库没了」。

## 二、根因：同一份约束写了三遍

| 层 | 位置 | `kind` 集合 |
|---|---|---|
| 工具 schema | `dist/index.js:67` | `env` · `tool-list` · `self-version` · **`path-exists`** |
| 探测实现 | `dist/anchors.js:33` | 有 `case 'path-exists'`（注释写明 0.12.0 加） |
| 存储 schema | `dist/engine.js:67` | `env` · `tool-list` · `self-version`（**漏了**） |

`path-exists` 是 0.12.0 新增能力，加的时候改了两处、漏了第三处。三份副本各自维护同一份集合，
漏改是**结构性必然**，不是这一次的疏忽。

## 三、三层缺口

| 缺口 | 表现 | 本可如何被拦住 |
|---|---|---|
| 写入端无校验 | 非法 anchor 落盘成功 | `blockSchema.safeParse` 在 `put` 前拒绝 |
| 打开失败静默 | 整个 domain 失联而无人知晓 | 失败至少 emit / 进日志 |
| 无存量校验 | 已经落盘的坏记录只能等下次打开时炸 | 离线扫描门 |

第二层比第一层更毒：这次能查出问题，靠的是「注入数 184 → 30」这个**恰好会被注意到的数字**。
若坏的是 global 域，或坏在没人数的角落，失联可以持续很久（见查证报告 §六的同类现象）。

## 四、三道门

### 4.1 门一：写入端校验

**做法**：把散在 create / patch / move / sweep / 迁移共 12 处的 `table.put(...)`（`engine.js:707, 810, 952,
1075, 1133, 1219, 1268, 1352, 1389, 1448, 1534, 1682`）收敛为一个私有方法：

```ts
private async putBlock(table, id, block) {
  const parsed = blockSchema.safeParse(block);
  if (!parsed.success) {
    throw new Error(`memory: refusing to store an invalid record ${id}: ${summarize(parsed.error)}`);
  }
  await table.put(id, parsed.data);
}
```

约束：

- **失败信息必须带 zod 的 issue**（哪个字段、什么值、期望什么）——排查成本的大头就在「从 domain 打不开倒推」；
- **不改 `put` 的调用语义**：`parsed.data` 回写，保证 strip/默认值行为与读路径一致；
- 迁移与迁移回退路径（`legacyDomainName` 分支）同样走它——那里的 block 来自旧文件，正是最可能不合规的。

**边界**：这道门拦不住「手改文件」和「降级内核后旧记录不被新 schema 接受」，所以门二、门三仍需要。

### 4.2 门二：打开失败可见化

**做法**：`projectTableFor(...).catch(() => undefined)` 这几处不再无声。至少：

- emit 一个事件（如 `memory/error`），带 domain 名与原始错误；
- 写进实例字段（如 `this.lastOpenError`），供 `memory_sweep` 与面板读取；
- `memory_sweep` 的报告里**声明数据完整性**：本次是否成功读到 project 侧——读不到时报告要显式标注
  「project 侧未纳入」，而不是给出一个看起来正常的偏小数字。

**为什么这是独立的一道**：门一只保证「新写入合法」，读不到表的成因还有存储损坏、并发句柄、
版本不匹配等。**读不到就说读不到**，比读到了但少一半更有价值。

### 4.3 门三：存量体检（check:rules）

**做法**：把本次用的一次性扫描器固化为仓库脚本（`scripts/check-memory-files.mjs`），
按 `blockSchema` 的约束逐条校验所有记忆文件：global（`$DSH_HOME/storages/memory.json`）+
各工作区（`<workspace>/.dsh/storages/memory_project_*.json`）。

- 只读，退出码 0 = 全绿 / 1 = 命中不合规 / 2 = 用法错误（沿用本仓库脚本约定）；
- 头部注释写明「能回答什么 / 判据怎么算 / 哪些情况答不了」（判据来源：协作约定「固化工具时必须带描述」）；
- 接入 `check:rules` 作为一门，与既有门同级。

**2026-09-25 一次性版本已跑过**：5 个文件 / 209 条记录 / 0 条不合规——存量是干净的，
这道门防的是未来。

### 4.4 治本：让约束同源

三处 `kind` 集合从**一处常量**派生：

```ts
export const ANCHOR_KINDS = ['env', 'tool-list', 'self-version', 'path-exists'] as const;
```

工具 schema 的 `enum`、探测 switch 的穷尽性检查（`default: assertNever(anchor.kind)`）、
存储 zod 的 `z.enum(ANCHOR_KINDS)` 全部引用它。**门能兜住这一次，同源才能拦住下一次。**

## 五、范围与测试

**最小可验证集**：

1. `putBlock` 单点校验 + 12 处调用点收敛；
2. `ANCHOR_KINDS` 常量 + 三处引用；
3. 打开失败 emit + `memory_sweep` 声明数据完整性；
4. `scripts/check-memory-files.mjs` + `check:rules` 登记。

**测试**：

- 写入非法 anchor 的 block → 抛错且**不落盘**（比对文件 mtime / 内容）；
- 合法 anchor（四个 kind 各一）→ 正常写入并可在下次打开时读回；
- 构造一条不合规记录 → 打开失败被 emit / `memory_sweep` 显式标注 project 侧缺失；
- 扫描器：全绿退出 0；注入一条坏记录后退出 1；
- 穷尽性：`ANCHOR_KINDS` 新增值时，探测 switch 的 `assertNever` 会在编译期报错。

## 六、未决

1. **`putBlock` 的失败是抛错还是降级**？抛错（推荐）——静默降级等于把「写入放行」的坑换了个位置；
   但要让调用方能看到明确原因，而不是又一次被 `.catch` 吞掉。
2. **门二的上报出口**：事件、日志、面板、`memory_sweep` 四处都做，还是先做一个？倾向
   **先做 `memory_sweep` 声明完整性**（模型是默认读者，见设计原则「人的角色是观察者」）。
3. **门三放哪个仓库**：`dsh-memory/scripts/`（与插件同源，能直接 import 编译后的 schema）
   还是 `SSiD/shell/scripts/`（与其它门同处）？倾向前者——**同源**比集中更重要。

### 三处偏离设计

**① 探测 switch 的 `default` 不是 `assertNever`，而是「编译期穷尽 + 运行期保守」。**

设计 §3.4 写的是 `default: assertNever(anchor.kind)`。但 `assertNever` 在**运行期会抛**——数据里可能躺着旧版本写下的未知 kind，探测跑在会话启动的校验路径上，那里不该因为一条坏记录把整个启动带崩。落地形态：

```ts
default: {
  const unhandled: never = anchor.kind   // 编译期：新增 kind 忘了加 case 会在这里报错
  void unhandled
  return undefined                        // 运行期：仍按「未校验」处理
}
```

**② 门二的失败记录点在 `projectTableFor` 内部，不在 3 个调用点。**

它仍然上抛（调用方的 `catch(() => undefined)` 语义一个字没改，所以三个调用点都不用动），只是**失败被记下来了**。好处是所有打开失败都经过这里，包括将来新增的调用点。

**③ 未决 1 的答案：抛错。** 已按推荐执行，理由写进了 `putBlock` 的 JSDoc。

### 一处实测发现：门二与门三互补

存储层封装后的错误消息实测是 `domain '…': stored record '<id>' in table 'blocks' does not match its schema`——给到 **domain 名 + 记录 id + 表名**，但**说不出字段级原因**（§4.1 期望的「哪个字段、什么值、期望什么」它给不出）。所以两道门的分工是：**门二答「有没有坏」，门三答「坏在哪」**。离线扫描器用同一份 `blockSchema`，能给出 `anchor.kind: Invalid option: expected one of "env"|…`。

### 未决 2、3 的答案

- **未决 2（门二上报出口）**：按倾向先做 `memory_sweep` 声明完整性。事件与日志未做——`projectOpenErrors` 已经把状态留住了，要加随时能加。
- **未决 3（门三放哪个仓库）**：`dsh-memory/scripts/`，按倾向选了**同源**（直接 import 编译后的 `blockSchema`）。代价是运行前要先 build，所以 script 写成 `npm run build && node …`。
