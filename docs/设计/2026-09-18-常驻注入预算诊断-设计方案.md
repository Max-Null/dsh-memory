# 常驻注入的预算诊断与清理：设计方案（2026-09-18）

> 状态：**设计待评审**（未实现）
> 关联：`docs/决策/2026-09-18-常驻注入判据.md`（§六 预算约束）、`src/injection.ts`

## 一、目标

让「哪些常驻记忆实际没进上下文」在**每轮都看得见**，代价是一行约 100 字符的诊断；清理动作复用已有能力（`memory_update(id, injected=false)`），不新增机制。

**非目标**：改注入排序规则、给记忆加优先级字段、自动撤下显式钉入的条目、引入定时器或后台任务。

## 二、设计依据：三个反例

**反例 1 —— 以为在场，其实不在场。**
2026-09-18 实测：project 库 17 条 `injected: true` + global 2 条，而注入列表只有 11 条。8 条常驻记忆出局这件事**没有任何人知道**——模型不知道（注入上下文里既没有它们、也没有说明），用户不知道（面板只显示「省略 N 条」这个数字，没有明细）。「钉住常驻」被默认理解成了「每轮在场」，而它在预算不足时只是「有资格排队」。

**反例 2 —— 出局顺序由「最近更新」决定，与重要度无关。**
`renderInjection` 按 `lastUsedAt ?? updatedAt` 降序取。`1c19d2f8`（「DSH 源码只引用不改」，铁律级）因为很久没更新而排到末尾出局。**越稳定的约定越容易被挤掉**——这恰好与「规则类更需要常驻」相反。好在 AGENTS.md 里有冗余，但冗余是运气，不是机制。

**反例 3 —— 清理没有触发点。**
30 天未命中会自动降级，但只对 `injectedAuto: true` 的条目；人工或模型显式钉入的（`injectedAuto: false`）没有任何自动清理。这是**设计意图**（有意决定不该被系统推翻），但也意味着它们只能靠人想起来清——而「想起来」正是这类机制最容易失败的地方。

## 三、机制设计

### 3.1 诊断行（核心）

`renderInjection` 增加返回值 `omittedIds: string[]`（纯函数，被预算跳过的条目 id，按渲染顺序）。`recallText` 在注入行之后追加一行：

```text
（另有 8 条常驻因预算未注入：1c19d2f8, d70da933, 8d0b8607, 242b0c20, 7bcaf99d, 5cbed5d2, 3a8999c1, …）
```

约束：

- **只在 `omitted > 0` 时出现** → 清理干净即消失（自消除，不产生永久噪音）。
- **不占注入预算**：它是诊断而非记忆。若占预算，会出现「诊断挤掉记忆 → 更多记忆出局 → 诊断更长」的递归。
- **id 截断到前 12 个**，超出以 `…` 结尾，防止极端情况下这行本身失控。
- 放在 `memory:recall`（动态 context），**不放 `memory:self`**——后者是每轮一字不差的固定前缀，塞动态内容会破坏提示缓存。

### 3.2 面板明细

`injectionPreview` 现在返回 `omitted: number`。**新增 `omittedRecords: Array<{ id, namespace, summary }>`**，保留 `omitted` 不动（既有 client 已在用，避免破坏式变更）。面板把「（省略 N 条）」做成可展开列表，用户能对照 id 与摘要。

**为什么注入行只给 id、不给摘要**：模型侧要拿 19 条常驻的完整内容需一次 `memory_list({injected:true})`（约 4000 字符），而 id 列表约 100 字符——差 40 倍。id 已够定位，摘要留给按需查询与面板。

### 3.3 清理判据（复用既有，不新增）

对诊断行列出的每一条，问**与钉入时同一个问句的反面**：

> 这条没进注入，我会不会漏掉它？

- **会** → 留下，并且它通常说明排序偏了——这时该考虑撤掉某条更靠前的参考类，而不是把这条也牺牲掉。
- **不会** → `memory_update(id, injected: false)` 撤下。

### 3.4 触发（事件驱动，不引入定时器）

诊断行每轮可见即是触发。把「看到诊断行 → 在合适会话里评估清理」并入判据记忆 `052e413c` 的正文，**不新增常驻条目**——否则又是预算消耗，与目的相悖。

## 四、原则（供后续改动判断是否推翻）

1. **诊断可见但不占地**：一行字符量级，且自消除。
2. **只暴露事实，不替人决定**：系统报告谁出局，但不自动撤 `injectedAuto: false` 的条目。
3. **复用而非新增**：执行走 `memory_update`，触发走已有判据记忆；不引入新工具、新存储、新定时器。
4. **id 优先于摘要**：上下文是稀缺资源，能靠 id 定位就不带正文。

## 五、第一版范围（最小可验证集）

- `renderInjection` 返回 `omittedIds`
- `recallText` 追加诊断行（含 12 条截断）
- `injectionPreview`（`remote.ts` / `routes.ts`）返回 `omittedRecords`
- 面板：省略计数可展开
- 测试：无出局时无诊断行；有出局时行的 id 与 `omittedIds` 一致；`budget: null` 时无诊断；超过 12 条时的截断；诊断行不计入 `chars`
- 判据记忆 `052e413c` 正文补一句触发说明

**明确不做**：优先级字段、排序规则改动、自动清理、诊断行的开关配置。

## 六、未决

1. **诊断行要不要带摘要**（而非纯 id）？倾向不带——从约 100 字符涨到 400+，而 id 已够定位。
2. **「常驻上限」要不要也可见**（面板显示「常驻 19 / 可注入 11」）？倾向面板做、注入行不做——注入行只报异常（有出局），常态不占位。
3. **排序规则是否该引入重要度**？独立议题。一旦引入就要回答「谁定义重要度」，而把清理做干净比给排序加权重更简单。倾向前者。
