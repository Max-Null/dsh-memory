## 一、为什么要借阅别人的设计

不是为了找一个更好的实现照抄，而是为了**拿到一组不同的判据**——当两套设计对同一个问题给出不同答案时，差异会暴露双方各自默认了什么。

这次借到的两条判据，一条命中了真问题，一条让我误报：

| 它的判据 | 对我们的作用 |
|---|---|
| ★★ **「在没有真实分布时，拍任何数字都是误杀面」**（`write-admission.js` 阶段一：只计量不拦截） | **命中** → `AUTO_DEMOTE_DAYS = 30`（见第二节） |
| ★ **`minRefTimeMs`：按快照取、按快照写**（Sleep Mode 的分层降级） | **误报** → 怀疑 `demoteStaleInner` 的写回形态；查证后排除（见第三节） |

## 二、发现一：`AUTO_DEMOTE_DAYS = 30` 的溯源链

### 表面：注释声称与面板对齐

```ts
/** 自动降级的天数阈值（2026-09-15）：与面板的冷数据判定（COLD_DAYS=30）对齐。 */
const AUTO_DEMOTE_DAYS = 30
```

两边**互相声明对齐**：

- `src/engine.ts:242`：「与面板的冷数据判定（`COLD_DAYS=30`）对齐」
- `src/client/index.tsx:723`：「冷数据判定用 `isCold(lastUsedAt)`（引擎自动降级用同一个 30 天阈值）」

### 实际：两份独立常量，一致性靠注释维持

| 常量 | 位置 | 引入版本 |
|---|---|---|
| `COLD_DAYS = 30` | `src/client/index.tsx:569` | 0.5.3 |
| `AUTO_DEMOTE_DAYS = 30` | `src/engine.ts:243` | 2026-09-15 |

**两处各写一份 30，没有任何机械保证它们相等。** 这正是 dsh-mneme 反复强调的形态——「两处各写一份 list 迟早漂移成两套口径」（它的 `PINNED_MEMORY_TYPES` 导出、`peak-hours.js` 抽模块、`MIN_SIM` 同源，三处都是为这件事）。

### ★ 更重要的：这个数字的**代价不对等**

溯源到设计文档（`docs/设计/2026-09-15-静默记忆机制-设计方案.md:124`）：

> 「阈值取值：命中计数 N、跨会话 M、未命中 T（**建议** N=2、M=2、T=30 天，**与现有 `COLD_DAYS` 对齐**）。」

**所以当时的推理是**：面板已经有一个 30（用于折叠界面），那行为阈值也用它吧。

**但两者的代价完全不同**：

| | `COLD_DAYS = 30`（面板） | `AUTO_DEMOTE_DAYS = 30`（引擎） |
|---|---|---|
| 触发后发生什么 | 该组**折叠起来** | **撤掉常驻注入**（`injected: false, injectedAuto: false`） |
| 代价 | 点一下就能展开 | **0.12.0 取消自动升之后，被降下就基本不会自己回来** |
| 可逆性 | 完全可逆 | 需要人（或模型）显式重新钉入 |
| 面向 | 展示 | **行为** |

**一个用于界面折叠的展示阈值，被提升成了自动撤销注入的行为阈值。**

而且同一份设计文档里，`T=30` 与 `N=2` 是并列的「建议」——**`N=2` 的那条已经被证伪并删除**（0.12.0 取消自动升，理由是「命中次数度量的是『它被想起来了』，而常驻的语义是『它不能被忘』」），**而同批的 `T=30` 从未被同样审过**。

### 对照：同一个文件里两处**刻意不对齐**的阈值

同在 `engine.ts` 附近：

```ts
/**
 * 体检里「久未命中」的默认天数阈值（0.12.0）。
 *
 * 比自动降级的 30 天大得多，因为两者判的不是一类东西：30 天判「自动升上来的常驻是否还有
 * 价值」，而久未命中的对象**本来就不是常驻**——非常驻的记忆几十天不用是常态，阈值定得太低
 * 会把正常记录报成待清理。
 */
const DEFAULT_SWEEP_DAYS = 90
```

```ts
/**
 * ...
 * 与检索返回值解耦（返回值不动）。
 */
const HIT_MARK_LIMIT = 5
```

**这两处的注释都明确论证了「为什么不复用」，理由都是「判的不是一类东西」。** 也就是说，我们**已经有过这个判断力**——只是在 `AUTO_DEMOTE_DAYS` 那一处没应用。

### 待决

两条路，**互相不替代**：

| 路 | 解决 | 不解决 |
|---|---|---|
| **A. 把 30 提成共用常量**（如 `COLD_DAYS` 从 `engine.ts` 导出给面板） | 漂移风险 | **代价不对等** |
| **B. 按行为阈值的代价重新定一个数字** | 代价不对等 | 漂移风险（若不做 A） |

**倾向**：先 A 后 B，或者一起。做 B 时的判据已经在 `DEFAULT_SWEEP_DAYS` 的注释里示范过——**先问「这两个阈值判的是不是一类东西」，再决定能不能共用**。

**但要先说清一个前提**：无论选哪条，都缺**分布依据**。我们至今不知道「自动升上来的常驻，实际多久没命中会被降下来」，也不知道「降下来的那些是不是真的该降」。按 dsh-mneme 的判据，**在这两个数字拿到之前，任何新的 T 也都是拍的**。

### 已实施（0.13.0，2026-09-29）

**没有走 A，也没有走 B**——而是先把这个数字的作用停掉：

| 项 | 之前 | 之后 |
|---|---|---|
| `demoteStale` | 撤销常驻注入，返回撤了几条 | **只返回候选清单**（`AutoDemoteCandidate[]`，含 `idleDays`），**不修改任何状态** |
| 判据位置 | 内联在 `demoteStaleInner` 的循环里 | 抽成纯函数 `isAutoDemoteCandidate`，**体检与降级共用一份** |
| 体检（`sweep`） | 无此维度 | 新增 `autoDemoteCandidates`（含 `idleDays`）——**让那个数字变得可观察** |
| 启动维护日志 | 「长期未命中，撤下常驻 N 条」 | 「N 条常驻闲置超 30 天（只计量不生效；最久 M 天）」 |

**这样做的理由**：A（提共用常量）和 B（换新数字）都还在「拍」；而停掉它的作用**零风险且立刻可逆**，同时开始积累真正需要的那个分布。等 `autoDemoteCandidates` 里的 `idleDays` 攒出形状，再回来定阈值——那时定的才不是拍的。

**测试 166 → 168**，其中一例专门锁「体检全程只读」（连 `updatedAt` 都不写）。**负向验证已实测**：临时让 `demoteStale` 恢复撤销行为，1 例红在 `expected false to be true`，其余 64 例照旧为绿。

## 三、一次误报：`demoteStaleInner` 的写回窗口（已排除）

> **结论先行：这不是缺陷，`engine.ts` 无需改动。** 保留本节，因为排查过程本身有价值——
> 它说明「看着像竞态的代码」要靠什么才能被判定为不是竞态。

### 当初的怀疑

```ts
for (const table of tables) {
  // 先快照键值对：put 会改到底层 Map，边遍历边写不安全
  for (const [id, block] of [...table.entries()]) {        // ① 快照
    ...
    const last = block.lastUsedAt ?? block.updatedAt        // ② 用快照值判断
    if (last > threshold) continue
    await table.put(id, { ...block, injected: false, injectedAuto: false })  // ③ 用快照值写回
  }
}
```

局部形状确实可疑：**②与③之间隔着 `await`**，看似窗口覆盖整轮扫描；**③ 用整条快照写回**（`{ ...block }`），看似会回滚中途的内容改动——而且失败是静默的，`memory/changed` 事件照旧只报 `{ operation: 'injected', injected: false }`。

两层假想后果：

| 层 | 假想场景 | 假想后果 |
|---|---|---|
| ① 误降 | 快照后、写回前，该条被检索命中（`lastUsedAt` 更新为「刚刚」） | 仍按旧值判定 → 降级一条刚用过的记忆 |
| ② 内容回滚 | 快照后、写回前，该条被 `memory.update` 改了内容 | 写回旧内容 → 中途改动被静默丢弃 |

### 为什么它不成立：`writeScope` 串行化

```ts
/**
 * 一次写入的完整作用域：串行化 → 新鲜度门 → 执行 → 记指纹。
 * 刷新与「读—改—写」必须同处一个互斥区，否则并发写会在两者之间穿插。
 */
private writeScope<T>(projectCwd: string | undefined, run: () => Promise<T>): Promise<T> {
  const task = this.writeChain.then(async () => {
    await this.refreshForWrite(projectCwd)
    const result = await run()
    this.noteStoreStamps(projectCwd)
    return result
  })
  this.writeChain = task.then(() => undefined, () => undefined)
  return task
}
```

**所有**写路径都经过它——`remember` / `update` / `demoteStale` / `forget` / `setInjected` / `move` / `supersede` / `retract` / `setStatus` / `verifyAnchors` / `migrateLegacy`，无一例外——而 `writeChain` 把它们**串行化**。

**所以**：② 读到的值，在 ③ 写回时**不可能**已被本进程改过。两层假想后果都不成立。

### 那跨进程呢

`writeScope` 是**进程内**的。但它在每次进入时跑 `refreshForWrite`（新鲜度门，靠文件指纹检测外部实例是否改过存储），**所以跨进程也有协调**。

**剩下的窗口**：一轮扫描期间，另一个实例改了磁盘，而本进程在扫描中不重新检测。

**但这是有意的取舍**——注释写明「刷新与『读—改—写』必须同处一个互斥区」，刷新被设计成**进入时一次**而非每条一次（后者要为每条记忆付一次文件指纹检测）。

**而且「重读」修不了它**：`table.get(id)` 读的是本进程内存里的表，不是重新读磁盘——在跨进程场景下，重读同样是恒等操作。

### 我实际做了什么

先按「收集后写 + 重读」改了 `demoteStaleInner`，跑完门禁（166 例仍绿，因为无并发时新旧行为相同），**然后在写测试时去查 `writeScope` 的前提，发现整个怀疑不成立，原样还原**（`git diff -- src/engine.ts` 无痕迹）。

**留下的教训**：判定「这是不是一个竞态」，不能只看**局部代码的形状**，还要看**它所在的作用域**。这次的局部形状（快照 + `await` + 整条写回）确实像，但作用域提供了一个不变量，而我没有第一时间去查它。

**具体说**：`await table.put(...)` 让出的是**事件循环**，不是**互斥区**——在 `writeChain` 之下，其他写根本没机会拿到执行权。两者看起来都是「异步让出」，但一个能被插入，另一个不能。

## 四、B2：注入会不会被压缩回写（查证结论）

**结论：注入会进入压缩摘要的输入（确定）；但不会被自动回写成记忆（DSH 没有那条路径）。** 若只问「会不会自我强化」，答案是**不会**——但过程中确认了一个此前的成本盲区。

### 查证路径

`packages/compaction/compaction-basic/src/region.ts` 的 `buildSummarizationInput`：

```ts
/**
 * Reconstruct the last routed request's cacheable prefix for the shadowed
 * region: the system prompt held by the `system/message` at surface node 0,
 * the header's tool schemas, then the region's own derived messages in surface
 * order. ...
 */
const head = systemHead(session, session.surface.nodes[0]!)
const system = head === undefined ? null : session.deriveEventMessage(head)
```

**摘要输入 = 系统提示 + 工具 schema + 被压缩区间的消息。**

而 `summarizer.ts` 说明了为什么**刻意**这么做：

> 「Keeping the conversation's own system prompt, tools, and message prefix in front of it makes the auxiliary call a **genuine prefix of the last routed request**, so the provider's **KV cache is reused** instead of invalidated.」

**目的是复用 KV cache**——把上一次请求的逐字前缀重放一遍，只把压缩指令追加在末尾。所以它**不可能**排除系统提示。

### `system/message` 里存的是渲染结果

`session-format-v3-to-v4` 的测试样本给出了 payload 形状：

```ts
message: { id: 'system', role: 'system', source: { kind: 'system-prompt' }, content: [{ type: 'text', text: ... }] }
```

**存的是渲染好的文本**，不是「稍后重建的指令」。它位于 **surface node 0**（受保护的 head，只允许 replace），所以摘要读到的就是**当前那一份**——含 `memory:recall`。

### 但「回写成记忆」不成立

因为 DSH 的压缩链**不认识记忆**：

- 压缩的产物是一条 `user/message`（`checkpointMessage`，由 `frameSummary` 包装）——**会话消息，不是记忆**
- DSH 里没有「摘要 → `memory.save()`」这条边。有那条边的是 **dsh-mneme 自己的 `summarize.js`**（它在 `turn/end` 提炼偏好/决策并入库，并用 `source.kind = 'plugin'` 过滤掉插件注入）

**完整风险链**：

```
memory:recall 注入 → system/message 事件 → 压缩摘要输入 → 摘要文本 → user/message
                                                                        ↓
                                                      模型读到 →（模型主动）memory_save
```

**最后一环是模型主动的**，不是系统自动的。dsh-mneme 防的是**自动**那一环（注入物被下一轮蒸馏成记忆）；我们没有自动蒸馏，所以**不构成自我强化**。

### 一个此前的成本盲区

**注入内容会占压缩摘要的预算，并被反复摘要。**

- 每轮的注入（最多 1500 字符 + 诊断行）都在系统提示里，而系统提示是摘要输入的一部分
- 压缩发生时，模型要连注入一起压掉；多次压缩会反复处理它

这不是缺陷，是「复用 KV cache」这个目标的固有代价。记下来是因为它影响一个**尚未决定**的问题：**注入预算该多大**——预算越大，每轮成本和压缩时的成本都越大，而这条成本此前不在评估里。

（附注：`source.kind = 'system-prompt'` 是个现成的标记。若确实要在摘要侧排除注入，标记已经有了——但那会牺牲前缀缓存，需要另外权衡。）

## 五、顺带确认的（不是问题）

借阅过程中也对上了几处**我们本来就做对的**，记下来免得日后被别人的解法带偏：

| 我们的做法 | 它的对应 |
|---|---|
| `dist` 不入库 + `prepublishOnly` 现场 build | 它 `lib` 入库 + `check-sync` 平价锁（我们结构上避开了「忘记 sync 静默发旧代码」） |
| 敏感内容隔离 + 其余写入放行 | 它的硬拒只留「密钥/PII」与「空白噪声」——门判宽了会吃掉本该交给裁决的样本 |
| 判据用计数，不用相似度 | 「相似度阈值只会在两种误判之间来回挪」 |
| `injectedAuto: false` 双向豁免 | 它的 pinned 穿透口「整个不进闸门」 |
| `deriveSummary` 只截断不猜 | 「判不出就留空」 |
| `DEFAULT_SWEEP_DAYS = 90` 明确论证「为什么不像 30 那样复用」 | 同一种判断力的另一处应用 |
