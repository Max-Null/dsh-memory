# 云同步多端删除 — 修复设计（2026-11-14）

> 背景查证见 `2026-11-13-云同步多端删除-查证报告.md`（下称「查证报告」）。本文是**可执行的设计**：每一步改哪个文件、改成什么、测试怎么先红。
> 状态：**设计已定，未实现**。
> 前置版本：0.22.4（`861182e`）。

## 一、要解决的三件事

| # | 问题 | 现状 | 目标 |
|---|---|---|---|
| 1 | push 把「本机看不见」当成「已删除」 | `sync-writer.ts` 无条件删差集 | 远端记录只增不减，除非本端明确删过 |
| 2 | 墓碑判定拿别端快照当基线 | `.sync-state.json` 单份、随仓库走 | 每端只和自己的上一份状态比 |
| 3 | 墓碑只写不读 | `readIncoming` 只扫 `records/` | pull 消费墓碑，让 `memory_forget` 跨端生效 |

**三件事的依赖关系**：1 是止血；2 是 3 正确的前提（否则 3 一开就会用别端的删除记录删本端记忆）；3 是「删了又回来」的出口。必须一起做。

## 二、方案

### A. `writeMirror` 不再默认删差集

**改动**：`src/sync-writer.ts` 的写盘逻辑加 `allowDelete?: boolean`（默认 `false`），且删除目标从「差集」改为「显式待删列表」。

```ts
export interface MirrorWriteOptions {
  readonly targetDir: string
  readonly files: readonly SyncRecordFile[]
  /** 待删的相对路径（从 records/ 起算）。默认空 = 一个都不删。 */
  readonly remove?: readonly string[]
}
```

行为：

- `files` 里的每个文件照写（保持增量：内容相同则不写、不计 `written`）。
- **`records/` 下不在 `files` 里的文件一律保留**（旧行为会删掉，这是本设计要改掉的）。
- `remove` 里的路径才删（`rmSync`），且只删 `records/` 下的。
- 返回值里的 `removed` 只统计 `remove` 实际删掉的。

**为什么不做 `allowDelete` 开关而是改成 `remove` 显式列表**：开关型的 `allowDelete: true` 仍然要求调用方先算出「该删什么」——那个差集就是 bug 的来源。显式列表强迫调用方给出「谁被删了」的依据（本端 state 差集 + 墓碑），语义更硬。

### B. `.sync-state.json` 按端分片

**改动**：`src/sync-tombstone.ts` 的 state 读写加 `envName`：

- 路径：`<mirrorDir>/.sync-state.<envName>.json`（`envName` 经 `safeEnvName()` 归一化，非法字符替换为 `-`，长度截断到 32）。
- `readState/writeState` 接受 `envName` 参数。
- **不再读旧单份 `.sync-state.json`**——旧文件留在仓库里当历史，不迁移。理由见 §四。

**`envName` 的缺省值**：`resolveSyncConfig()` 里补：

```ts
const envName = typeof raw.envName === 'string' && raw.envName !== ''
  ? raw.envName
  : sanitizeEnvName(os.hostname())
```

否则两端都退化成 `local`，分片文件同名，B 等于白做。`os.hostname()` 为空时退回 `local`（极罕见）。

### C. pull 消费墓碑

**墓碑格式**（`src/sync-tombstone.ts`）：

```ts
export interface Tombstone {
  readonly id: string
  readonly scope: 'global' | 'project'
  /** project 记录所属项目名（global 为 undefined）。 */
  readonly project?: string
  readonly deletedAt: number
  /** 本端删除时的记录快照——pull 端删本地前先用它兜底，也方便人工恢复。 */
  readonly snapshot?: unknown
  /** 哪个环境删的；用于排查，不参与判定。 */
  readonly env?: string
}
```

**写入**（`syncPush`）：`planTombstones` 的输入改为「本端 state 与本次 files 的差集」，并为每条墓碑补 `snapshot`（从**本端**被删记录里取——需要 `collectMirror` 同时返回被删记录的原始内容，见 §三.2）。

**消费**（`syncPull`）：在 `planImport` 之后增加一步 `applyTombstones`：

```ts
for (const tombstone of readRemoteTombstones(config.mirrorDir)) {
  const local = await memory.locate(tombstone.id)   // 需要新增或复用既有按 id 定位
  if (local === undefined) continue                 // 本端没有，跳过
  await memory.forget(tombstone.id)                 // 复用 forget：它会写本地侧状态
}
```

**安全边界**：

1. 只删 **id 完全匹配**的记录（记忆 id 是 uuid，不会撞）。
2. 删除前把本地记录写进 `conflicts/`（命名 `deleted-<id>.json`），保留一次还原机会。
3. 墓碑本身留在仓库里（不删），重复 pull 幂等。
4. 如果本端记录的 `updatedAt` **晚于** `tombstone.deletedAt`，说明本端在那之后改过——**不删**，记入 `conflicts/` 等人处理（这是「改过的不该被旧删除覆盖」）。

## 三、已核对的代码事实（2026-11-14）

落笔前核对过，避免又出「报告说 A、代码是 B」：

1. **按 id 定位/删除**：`forget(id, projectCwd?)` 是公开方法、返回 boolean，**可直接复用**做 C 的删除。但要判断「本端记录是否晚于墓碑」，还需要读 `updatedAt`——`locateRecord` 是私有，需新增 `MemoryEngine.findById(id, projectCwd?)`（薄封装）。
2. **`collectMirror` 不改**：它只返回 `files`。C 的 `snapshot` 在 `syncPush` 里补——用本端 `previous - current` 得到被删 id，再 `findById` 反查记录内容。比改 `collectMirror` 干净。
3. **`dropTombstoned` 保留**：`writeState(dir, dropTombstoned(current, tombstones))`，作用是让新 state 不残留已墓碑的 id。C 之后它仍有意义（幂等），不动。

## 四、为什么不迁移旧 `.sync-state.json`

旧文件记录的是「最后一次 push 那一端的镜像全集」。把它当任何一端的「上次状态」都会踩回 3.3 的坑。

分片后每端首次 push 时 `previous === undefined` → `planTombstones` 的「首次永不产生墓碑」保护生效 → **不会误判**。旧文件留在仓库里，只作为历史；下一次 push 会写新的分片文件。

代价：迁移后第一次 push 不产生墓碑（本端之前删过的，不会马上传播）。可接受——比误删安全。
