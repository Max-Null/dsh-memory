# 记忆云同步 — 设计方案（2026-11-06）

> 状态：**多写者模型已定**（2026-11-11 由主从改来，理由见 §一）；导出层已落地但**项目名口径待重做**；传输层未开始（进度见 §九）。
> 起因：用户 2026-11-05 试用 dsh-go 手机端，确认记忆插件可装可用，但手机是**独立的库**——本机这份 300 余条记忆不会自己跟过去。提出用 GitHub 仓库做同步总线，理由是「走 merge 机制而不是整份覆盖，还能留版本记录」。
> 对照物：`dsh-memory-github`（primary/child + `notes/*.md` + git）、`dsh-mnemon`（ZIP 导出导入）、`sync-cs`（AES 整包 + REST）。

## 一、结论

用 **多写者（每个环境都能写）+ 一条记忆一个文件 + 项目名作跨机身份 + git 远端**。

**为什么不是最初定的主从。** 2026-11-06 的第一版是 primary/child 单写者——用结构消除冲突，而不是用合并解决冲突。那个取舍在「电脑 + 手机」两个环境时成立。2026-11-11 前提变了：用户置办了工作笔记本，环境至少五个（本机 / 本机 WSL / 手机 / 工作机 / 工作机 WSL），未来可能再加服务器；而且工作机不是纯消费端——它会跑思灵全家桶的开发环境、偶尔改 bug。

一主四从的代价随之变成：**四个环境里的模型不许写记忆**。而在工作机上解决 bug 那一刻的观察，恰恰是那个环境下最在场的东西——让它先写留言、等主端开机再整理，延迟太长，也可能永远等不到。所以放弃单写者。

**冲突面比想象中窄，这是多写者可行的前提**：

- **项目记忆**按**项目名**分目录（§四）。不同环境的不同项目天然是不同文件，不会撞。
- 真正会撞的只有**同一条 global 记忆被两个环境同时修改**——就是「他叫我宝贝」「判断类动作直接做」这类。低频，且按 §3.5 保守处理：留证、不自动裁决。
- 项目记忆的跨机身份定为**项目名**（`basename(cwd)`）。依据是用户 2026-11-11 的三条明确约束：「以项目名为准」「不会出现同名不同项目」「工作机上的目录不一样」。三条合起来排除了同名撞车，也就不需要 git remote 或路径映射表那套复杂度。

## 二、依据：整份 JSON 上 git 会撞，而且撞得危险

两个对照实验（真实 `memory.json` 格式，两端各新增一条记忆后 merge）：

| 形态 | merge 结果 |
|---|---|
| 整份 `memory.json` | `CONFLICT (content)`，2 处冲突 |
| 一条记忆一个文件 | `Merge made by the 'ort' strategy`，只新增 1 个文件，0 冲突 |

整份 JSON 的冲突形态尤其坏：两条记录挤在同一个插入点，按「取一边」解决会**静默丢掉另一端那条**，而 git 仍报「合并成功」。若解决时破坏了 JSON 结构，还会让整个库读不出来（对应 `blockSchema` 门三的整块拒绝）。

**但一条一文件只解决了「各自新增」。**「同一条被两端修改」仍是同一个文件被两边改，仍会冲突。社区的三个实现没有一个做多写者：

- `dsh-memory-github`：primary 写并推，child 只读 + 写 `inbox/`
- `dsh-mnemon`：ZIP 导出导入，推拉都要人工确认
- `sync-cs`：打开自动拉、回合结束推（其冲突策略未查证）

所以本方案不引入冲突裁决，而是**消除冲突的来源**。

## 三、关键判据

### 3.1 删除留墓碑，不直接删文件

`dsh-memory` 有两套删除语义，**必须分清**：

| 通道 | 实现 | 同步时会怎样 |
|---|---|---|
| `memory_forget` | `table.delete(id)` —— 记录真的消失 | 与「另一端刚加、我还没拉到」无法区分 |
| `memory_update(retract)` / `supersede` | `markStale()` → `stale: true` + `staleReason` | 记录保留，天然可同步 |

`blockSchema` 的 `status` 只有 `suggested / approved / auto / suggest`，**没有 deleted 状态**，也没有墓碑字段。

多写者下这个歧义必须在同步层消掉：本地「git 里有、我这儿没有」既可能是本机删了，也可能是另一端刚加的还没拉到——而两种情况的正确动作完全相反（删远端 vs 拉下来）。

做法：同步层维护一份**上次同步时的 id 快照**。push 前对比出「曾同步过、现在本地没了」的 id，在 `records/` 下写一份墓碑（`deletedAt` + 删前内容），**不删文件**。这样删除变成「文件被修改」，与「另一端改了同一条」是同一类冲突，避开更难处理的 modify/delete 冲突。

### 3.2 `index.json` 可以存在，前提是可重建

`dsh-memory-github` 保留了 `index.json` 并做了「从 `notes/` 重建」的自愈。这比「绝对不要索引文件」更实用：

- 索引是**派生品**，不是事实源
- 冲突了、丢了、坏了 → 从 `records/` 扫一遍重建
- 两端新增时即使索引发生冲突，也不是数据损失

判据：**任何进入同步面的文件，若损坏后可完全重建，它就不构成风险。**

### 3.3 冲突留证，不自动裁决

同一条被两个环境同时修改时，git 报 content 冲突。**不自动取新，也不取旧**——记忆是长期资产，被静默覆盖掉的那一份就没了。

做法：两边版本都写进 `conflicts/<uuid>.<环境标识>.json`，`records/` 里保留本机版本并标记待裁决。代价是冲突会堆到有人处理为止。

依据是用户 2026-11-06 明示的「做事要留痕」：加工链上的中间产物默认保留而不是清理，除非体量本身成了问题。

### 3.4 每个环境都是完整写者

早期版本设想过 primary / child 分工（写者 + 只读留言者）。多写者下这个分层取消：五个环境都能直接写记忆、都能推送。

代价是接受 §3.3 的冲突处理成本；换来的是「在任何环境里想起什么就能记下来」，不必等某个特定的端开机。

## 四、存储形态

```
<repo>/
  records/
    global/
      <uuid>.json                    一条一文件；各自新增互不相干
    project/
      <project-name>/                跨机身份 = 项目名（basename(cwd)）
        <uuid>.json
  conflicts/
    <uuid>.<env>.json                同一条被两端改时的双方版本（§3.3）
  index.json                         派生品，可从 records/ 重建
```

**`project-name` 是项目目录名，不是路径哈希。** 依据见 §一：用户 2026-11-11 明确「以项目名为准、不会出现同名不同项目、工作机上的目录不一样」。本机 `H:\MaxNull\WorkStation` 与工作机 `D:\WorkStation` 因此是**同一个项目**，记忆能对上；而现在的本地文件名仍是 `<cwd hash>`（`memory_project_3rf76j.json`），两者不同源，所以**本地存储不用动，只在同步面上算项目名**。

**一条记忆一个 JSON 文件**，内容与 `blockSchema` 同构。不用 Markdown：记录字段含 `keywords` 数组、`anchor` 对象、`topic` 自由字符串，frontmatter 表达这些会别扭，且需要另一套解析器——而 `schema.ts` 的判据已经存在，JSON 可以直接复用。

## 五、传输层：插件自带 git

三条路，选 isomorphism-git。

| 方案 | 依赖 | 体积 | 离线 | 本地历史 |
|---|---|---|---|---|
| 调系统 `git` | 机器上要装 git | 0 | ✓ | ✓ |
| **isomorphic-git** | 无 —— 纯 JS，有 Node 即可 | ~4.85 MB | ✓ | ✓ |
| GitHub REST | 无 | ~0 | ✗ | ✗ 历史只在远端 |

选它的理由不是「体积可接受」，是**依赖的性质**：

1. **插件是给别人用的。** 别人机器上没有我们的目录结构、没有配好的凭据，也不该被要求先装一堆系统工具。GitHub（或任意 git 远端）是唯一一个零运维、免费、人人可用的公共后端；换成自建服务等于要求使用者先有台服务器，那会把可用人群直接砍掉。
2. **系统 `git` 在移动端不可靠。** dsh-go 的本机运行是「App 内装 Ubuntu + Node.js + DSH 运行环境」，但它的更新说明写明换运行时会清掉 apt 装的软件（[v1.0.10](https://github.com/ccch1mneyyy/dsh-Go/releases/tag/v1.0.10)）。一个会被下次更新清掉的依赖，不该是同步链的地基。
3. **isomorphic-git 读写同一套磁盘格式**，所以本地仓库仍是真 git 仓库：`git log` / `git diff` 可读，离线可用。

代价 ~4.85 MB（未压缩）。用**动态 import** 稀释：没开同步的人不加载它。导出层不引入它——导出是纯函数，引入点在实现 push / pull 的那一步。

## 六、同步面只导出内容字段

**用白名单，不用黑名单。** `StoredBlock` 会持续长出新字段（`topic` 就是 0.20.0 才加的），黑名单会让新字段**默认泄漏**进远端——而「一个只该存在本地的字段漏进远端仓库」这类事故，被发现时内容已经在别人能拉到的地方了。

进镜像的字段：

```
namespace / status / content / keywords / createdAt / updatedAt
+ 可选：injected / injectedAuto / topic / kind / anchor / stale / staleReason / source / meta
```

**不进**：`hitCount`、`lastUsedAt`、`vector`。前两个是本地行为统计，每次检索命中都会改——带上它们会让 `records/` 在内容毫无变化时持续变脏，git 历史被噪声淹没；`vector` 是本地嵌入产物，体积大且可从 `content` 重算。

**隔离记录整条不导出**（`quarantined: true`）。隔离区存在的理由就是它可能含凭据类内容；推到远端仓库等于把那层保护绕开。代价是对端少几条，但隔离记录本来就不参与注入与检索，这个代价可以接受。

这一条同时解决了「整份 `memory.json` 上 git 会永远 dirty」的老问题。

## 七、工具面（不向模型暴露 git）

模型不该自己拼 `git pull --rebase && git add && git commit && git push`——那是把实现细节漏到模型层，出错难排查，也容易越权。

每个环境（五个都一样）只有两个同步工具：

| 工具 | 作用 |
|---|---|
| `memory_sync` | `action: status \| pull \| push`——查状态、拉取、推送 |
| `memory_conflicts` | `action: list \| resolve`——列待裁决的冲突，逐条选一边或保留两者 |

`memory_conflicts` 是 §3.3 的出口：冲突不自动裁决，但也不能只堆在那里没人看见——没有这个工具，`conflicts/` 就是个逐渐腐烂的目录。

## 八、配置

```yaml
memory:
  sync:
    remote: ''               # git remote（https + PAT）
    branch: main
    envName: ''              # 本环境的短名，冲突留证时用作后缀（如 本机 / 工作机）
    autoPull: true           # 启动时 pull
    autoPush: false          # 写入后自动 push（默认关，见下）
```

没有 `role`——多写者下每个环境平等。

`envName` 只影响 `conflicts/<uuid>.<env>.json` 的命名，不参与任何判定。留空时退回主机名。

`autoPush` 默认**关闭**：记忆写错比没写更坏，推到远端之前应当有一次人看得见的确认。`autoPull` 默认开启：读旧数据的风险远低于写坏。

### 9.2 待实施（按依赖顺序，前一步不落地，后一步无法验证）

#### 第 1 步 · 写盘层

把 `exportRecords()` 的输出落到磁盘上的镜像目录。

- **新增** `src/sync-writer.ts`
- 接口：`writeMirror({ targetDir, files }) → { written, removed, unchanged }`
- **必须增量**：内容相同的文件不重写——否则每次都是一批 mtime 变动，git 看起来像全量改动
- **必须处理删除**：本地 `memory_forget` 掉的记录，镜像里对应的文件要删。删除要**先算差集再动手**，不能边扫边删
- 不碰 `conflicts/` 与 `index.json`——它们不归写盘层管
- 验收：连续两次写同一份数据，第二次 `written === 0`；删掉一条记录后重写，对应文件消失、其余文件 mtime 不变

#### 第 2 步 · 本地 git 仓库

用 isomorphic-git 在镜像目录里 `init` / `add` / `commit`。**这一步不联网**，所以能在完全离线的情况下把整条链路验通。

- **新增** `src/sync-git.ts`；`isomorphic-git` 走**动态 import**（体积理由见 §五）
- 接口：`commitMirror({ dir, message }) → { committed: boolean, sha?: string }`
- 无改动时不产生空提交（`committed: false`）
- 验收：首次 commit 成功；无改动时 `committed: false`；改内容后产生新 commit 且 `git log` 可读
- 坑：isomorphic-git 没有可读的全局 git 配置，`author` 必须显式传

#### 第 3 步 · 远端 push

- 认证走 **PAT（https）**，不用 SSH——SSH key 在移动端的管理成本远高于 token
- token 从既有 credentials 机制取，**不写进 profile 配置**（§十一 最后一条）
- 验收：push 后远端出现 `records/`；无改动时再次 push 不产生空提交
- 坑：网络失败要能区分「认证错」与「连不上」，否则排查全靠猜

#### 第 4 步 · pull 与导入层

把远端拉下来写进本地库。**这是唯一会写本地记忆库的一步，风险最高，放在最后做。**

- **新增** `src/sync-import.ts`：`records/*.json` → 待写入的 block 列表
- 走引擎已有的写入路径，**不直接改 `memory.json`**——直接改文件会与内存缓存打架
- **冲突策略**（§3.3）：同 id 但内容不同 → 两个版本都写进 `conflicts/`，`records/` 保留本机版本并标待裁决。**不自动取新**
- **项目目录名 → 本地 cwd 的解析**：`records/project/<name>/` 要落到本机同名项目的 cwd 上。本机没有这个项目时不导入（留着文件等它出现），不是丢掉
- 验收：导入后 `memory_search` 能检索到新记录；重复导入不产生重复记录；冲突会出现在 `memory_conflicts list` 里
- 坑：导入必须**幂等**——同一批 records 导入两次，第二次应当无变化

#### 第 5 步 · 墓碑与删除

实现 §3.1。放在写盘层之后、工具面之前。

- 维护「上次同步时的 id 快照」，落在同步仓库的 `.sync-state.json`（随 git 走）
- push 前对比出「曾同步过、现在本地没了」的 id → 写墓碑，**不删文件**
- 验收：`memory_forget` 一条 → push → 远端出现墓碑而不是文件消失；另一端 pull 后该条不再出现在检索里

#### 第 6 步 · 工具面

- `memory_sync`（`status` / `pull` / `push`）
- `memory_conflicts`（`list` / `resolve`）——§3.3 的出口

每个工具都要有 `inputSchema`、`presentCall` 文案、以及一条端到端用例。

#### 第 7 步 · 冲突与墓碑的注入提示

pull 后检查 `conflicts/` 与未裁决墓碑，有则进注入提示。形态参照现有的「另有 N 条常驻因预算未注入」那一行——但**必须自带可操作性**（共几条、最早一条多久了），否则又是个只会增长的数字。

### 9.3 验证节奏

- 第 1、2 步在本地完全可验，不需要网络、不需要第二个设备。**先把这两步做扎实**：它们是整条链最容易出静默错误的地方（写盘层静默少写一份、git 层静默产生空提交）。
- 第 3 步需要一次真实 push。先推到临时私有仓库，别拿正式那份试。
- 第 4、5 步**必须**先在隔离环境验证（`.ssid-iso-test` 那套）——它们会写本地记忆库，出错等于动数据。
- 第 6、7 步才涉及多环境；到那时「手机 / 工作机能不能跑」才算真的可验（§十 第 1 条）。

## 十、未决与待验证

1. **手机端能否跑 isomorphic-git 的 push**——要验的是网络权限、TLS、token 三样，而不是「系统里有没有 git」（传输层选型见 §五，系统 git 已不再作为前提）。由于插件能力尚未实现，这一项只能等传输层落地后再验，不能反过来先验。
2. **WSL 与 Windows 算不算同一个环境**——同一台机器上两边各有自己的 `DSH_HOME`，若都写记忆，它们是两个写者，项目名的口径也不同（WSL 里路径是 `/mnt/h/...`，`basename` 可能对得上也可能对不上）。需要在真机上确认一次。
3. **冲突提示的注入形态**与预算占用（§3.3 的出口）。
4. ~~`workspace-hash` 的口径~~ —— **已定 2026-11-11**：改用项目名 `basename(cwd)`，依据见 §一。本地文件名不动。

## 十一、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 多环境记忆不一致 | 某个环境看到的是上次同步的快照 | 接受；用 `memory_sync status` 暴露滞后时长 |
| 冲突堆积无人处理 | `conflicts/` 变成腐烂目录 | pull 后进注入提示（§3.3 / 第 7 步） |
| 项目名撞车 | 两台机器上出现同名但不同的目录 | 用户 2026-11-11 明确不会发生；若将来出现，`conflicts/` 里会有痕迹 |
| 删除与未同步混淆 | 本机删了 vs 另一端刚加 | 墓碑 + 上次同步 id 快照（§3.1） |
| 仓库含个人记忆 | 推送到 GitHub 即离开本机 | 私有仓库；凭据走既有 credentials 机制，不写进配置 |
