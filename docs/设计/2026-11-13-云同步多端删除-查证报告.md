> 版本：0.22.4（`76d5b19 feat(sync): 云同步支持代理 + 面板加「测试连接」`）

## 一、结论

`syncPush` 以「本机当前可见的记忆」作为镜像的**全集**重建 `records/`，凡远端有、本机这次没收集到的记录一律 `rmSync` 删除。而「本机可见」的 project 部分来自 `engine.projectCwds()`——**仅包含本进程运行期间打开过的工作区表**。

两者叠加：多端（或多工作区）场景下，每次 push 会删掉另一端全部 project 记录；project 记忆因此**无法跨设备同步**，两端在两种状态间震荡。

`global` 不受影响（`collectMirror` 取全量），所以现象会呈现为「global 同步了，project 没同步」——一个容易误判为「对端没写过」的假象。

**当前远端仓库未被破坏**：本机从未执行过 push，`~/.dsh/memory-sync` 至今不存在。

## 三、根因

### 3.1 push 把「本机看不见」等同于「已删除」

`src/sync-writer.ts:72-110`：

```ts
const stale = scan(recordsRoot, RECORDS_DIR).filter(path => !wanted.has(path))   // :80
...
for (const relativePath of stale) { rmSync(join(options.targetDir, relativePath), { force: true }) }   // :100-107
```

`records/` 下任何不在 `wanted` 里的文件都被删除。没有白名单、没有「只写不删」模式、也没有把删除限制在「本端确实删过」的 id 上。

`wanted` 来自 `src/sync-service.ts:217-218`：

```ts
const files = await collectMirror(memory)
const write = writeMirror({ targetDir: config.mirrorDir, files })
```

镜像的语义被实现成了「本机记忆的完整投影」，而不是「在远端现状上的增量提交」。

### 3.2 project 部分只覆盖「本进程打开过的工作区」

`src/sync-service.ts:116-125`：

```ts
for (const cwd of memory.projectCwds()) {
  const records = await memory.list({ namespace: 'project' }, cwd)
  if (records.length === 0) continue
  projectDocuments.push({ cwd, document: recordsToDocument(records) })
}
```

`src/engine.ts:323-325`：

```ts
projectCwds() { return [...this.projectTables.keys()] }
```

`projectTables` 是**懒打开的内存缓存**（`projectTableFor` 里 `set`），既不是磁盘扫描，也不是全部已注册工作区。于是本次进程没打开过的工作区，其 project 记忆不会进 `wanted`，在 3.1 下被当作 stale 删除——**单机多工作区同样中招**，不必两台设备。

### 3.3 墓碑的 `previous` 指向的是「另一端的快照」

`src/sync-service.ts:220-225`：

```ts
const previous = readState(config.mirrorDir)     // 读的是仓库里随仓库走的 .sync-state.json
const current = stateOfFiles(files)
const tombstones = planTombstones({ previous, current, at: now })
```

`src/sync-tombstone.ts:63-81`：凡 `previous` 有、`current` 没有的 id，都判为「本端删了」，写一条墓碑。

`.sync-state.json` 随仓库走，记录的是**上一次执行 push 的那一端**的镜像 id 集合。本机首次 push 时 `previous` 是对端全集、`current` 是本机十几条 → 对端每条记录都被判成「本端删除」。

`planTombstones:56-58` 的注释已经写明这个失败模式（「把所有『远端有、本地没有』都判成删除会把另一端刚记的东西全删掉」），并给出保护条件「首次同步（`previous` 为空）永不产生墓碑」。问题在于：**该条件在跨设备场景下不成立**——镜像目录是 clone 出来的，`previous` 从第一天起就有值。保护条件与实际触发条件错配。

### 3.4 墓碑没有消费方

`src/sync-service.ts:270` 的 `readIncoming` 只扫 `records/`；`TOMBSTONE_DIR` 在整个 `src/` 里只出现在 `writeTombstones`（:169-176）与 `syncStatus` 的计数里。**pull 从不读取墓碑**，也不据它删除任何东西。

所以墓碑目前是只写不读的半成品：它们留在仓库里、被 `memory_sync status` 计入 `tombstones`，但没有任何代码路径消费。

### 3.5 `orphaned` 只保护了 import 侧

- `src/sync-import.ts:113-130` 的 `planImport`：本地没有同名项目 → `orphaned`，不导入、不报错、留在远端（正确）。
- `syncPush`：本地没有同名项目 → 直接删除远端记录（缺失对应保护）。

`orphaned` 的语义是「它存在，只是这台机器上落不了地」，而 push 把它当成了「已被删除」。

## 四、与设计文档的偏差

对照 `docs/设计/2026-11-06-记忆云同步-设计方案.md`：

| 设计条款 | 设计原话 | 实现 | 性质 |
|---|---|---|---|
| §3.1 | 「写一份墓碑…**不删文件**」 | `writeMirror` 直接 `rmSync` | **实现偏离设计**：删除绕过了墓碑通道 |
| §一 | 「不同环境的不同项目天然是不同文件，不会撞」 | 差集删除按本机全集算 | **设计内部矛盾**：假设了「不撞」，未假设「不删」 |
| §3.1 | 墓碑含「`deletedAt` + 删前内容」 | 只有 `id / scope / deletedAt` | 有意省略（理由：内容在 git 历史里），但删除后无法从墓碑恢复 |
| §8 | `envName`「只影响 conflicts 的命名，**不参与任何判定**」 | same | 多端共用一个 state 文件，正是 3.3 的根源 |
| §9.2 | 端到端「319 条真实记录推成功」 | 单端验证 | 多端路径从未验证（§9.4 第 6 步尚未执行） |

第三条的取舍可以接受（git 历史能恢复），但第一、二条不能：设计明确写了「不删文件」，实现却把删除做进了写盘层；而「项目集合可以不同」这个前提是 §一 多写者成立的依据之一，写盘层却按「全集替换」实现。

## 五、后果

| 场景 | 后果 | 自愈性 |
|---|---|---|
| 跨设备、工作区集合不同 | 每次 push 抹掉对方 project 记录；project 记忆无法互通 | 对方再 push 会写回，但随即抹掉本端——永久震荡 |
| 同一设备、多个工作区 | 未打开工作区的 project 记录被删 | 下次打开该工作区再 push 可写回 |
| 远端被删的记录 | 只剩 git 历史 | 需人工 `git revert` / `checkout`，插件无入口 |
| 对端本地记忆库 | **不受影响**（`planImport` 只产生 upserts，从不删除） | — |
| global 记忆 | 不受影响 | — |

## 六、修复方案

### 方案 A｜push 改并集基线，删除只由显式删除事件驱动

在 `syncPush` 里把远端现有记录并入待写集合，删除只对「本端确实删过」的 id 生效：

```ts
// 伪代码
const remoteExisting = scan(join(config.mirrorDir, 'records'), 'records')   // clone/pull 后的现状
const wantedSet = new Set(files.map(f => normalize(f.path)))
const retained = remoteExisting.filter(p => !wantedSet.has(p))              // 保留，不删
// 删除集合 = 墓碑里记录的 id；没有墓碑就不删
```

配套：`writeMirror` 增加 `allowDelete?: boolean`（默认 `false`），语义变成「写待写集合，可选地删除本端确认删除的」。

### 方案 B｜`.sync-state.json` 按端分片

改为 `.sync-state.<envName>.json`，`planTombstones` 只与本端上一份状态比对。这直接修掉 3.3——两端互不拿对方的全集当自己的删除依据。`envName` 已有配置项（§八），需要把它的语义从「冲突文件后缀」扩展为「本端身份」。

### 方案 C｜让墓碑真正被消费

若墓碑要保留（用来表达 `memory_forget` 的传播），`syncPull` 需要在 `planImport` 之后增加一步应用远端墓碑：对匹配 scope/项目名的墓碑 id，删除本地对应记忆（或标记而非真删，需产品决策）。

**当前实现里墓碑是只写不读的半成品——要么补齐消费侧，要么移除，不要让 `syncStatus` 报一个永远不生效的计数。**

### 推荐组合

**A + B**，能立刻止血且改动局部：远端不再被抹、两端不再互相判删。C 涉及产品决策（`memory_forget` 该不该跨端传播），可以单独一步做。

### 需要确认的一点

「镜像 = 本机投影」这个前提要不要保留？如果保留，同步就只能 union 不能 replace。若要支持「A 删了 B 也删」，唯一正确路径是**带端标识的墓碑 + pull 侧消费**，不能靠全量投影推断。

## 七、测试影响

`test/sync-writer.spec.ts:67-77` 明确锁定了「磁盘上多出来的记录被删掉（删除先算差集）」，断言 `removed: 1` 且文件不存在。

方案 A 落地后这条测试要拆成两条：

- 默认（`allowDelete` 未传）：磁盘上多出来的记录**保留**，`removed: 0`
- 显式 `allowDelete: true` + 待删列表命中：才删除

`test/sync-tombstone.spec.ts` 需要补一条「`previous` 来自另一端」的用例——现有用例只覆盖了 `previous === undefined`（首次同步），而跨设备场景恰恰是 `previous` 有值且属于另一端的形态。

`test/sync-service.spec.ts` 需要补一条端到端用例：模拟两个工作区集合不同的 engine，A push 后 B 的记录仍在。

## 八、验证清单

1. **跨端不互相抹除**：设备 A（工作区 1）push → 远端仍有设备 B（工作区 2）的 records；B push → A 的仍在。
2. **project 记忆能同步**（主验证点）：A 写一条 project 记忆 → push → B pull → B 在同名工作区能看到。当前实现下这一步**必然失败**。
3. **未打开工作区不被删**：单机两个工作区，只打开一个后 push，另一个的 records 仍在。
4. **墓碑语义**：A `memory_forget` 一条 → push → B pull 后该条在 B 被正确删除（或按产品决策标记）；未被删的不受墓碑影响。
5. **增量写保持**：连续两次 push（内容不变），第二次 `written: 0 / unchanged: N`，`git log` 不产生空提交。
6. **两个方向的首次同步**：镜像目录不存在时 push / pull 都能 clone（实测：直连超时需代理；ls-remote 通过不代表 clone 通过）。
7. **多工作区项目名对齐**：`H:\MaxNull\WorkStation` 与 `D:\WorkStation` 仍归同一 `records/project/workstation/`（已有的跨盘符判据不能被破坏）。
