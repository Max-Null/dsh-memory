## 一、范围

四段一起发：**准入**（取消自动升）、**在场**（排序去掉检索记录 + 时间可见）、**退场**（锚点扩型 + 语义作废）、**体检**（只读体检报告），外加**时间可筛**（`memory_list` 过滤）。

**不做**：面板清单、归档、时间感知检索、recency 权重、记忆日。面板在本插件的定位是**例外干预通道**（人撤常驻、删记录时用），**不是体检报告的常态读者**——读者说明见步骤 4。

**对上位文档的两处调整**（实现时发现，理由在此）：

1. **候选进注入诊断行，但只报数量与前几条摘要**。候选是「该不该钉」的待办，而**判断者是模型本身**——一份不会主动去调的体检报告等于不存在，可发现性是它存在的全部意义。诊断行给一行常数长度的提示（数量 + 前 3 条摘要），完整清单仍在 `memory_sweep` 里。放弃「不列候选以免噪音」的初衷：候选会随着被钉住或记录消失而自然减少，**噪音是暂时的，看不见是永久的**。
2. **sweep 每个会话跑一次**，频次由既有的 `maintenanceDone` 守卫决定（`engine.ts:988`，`runMaintenanceOnce` 的第一行）——不新增「每日一次」的时间戳，也不新增定时器。会话启动路径本来就在做锚点批量校验，sweep 搭同一次遍历。

两处调整都指向同一个判断：**注入诊断行只留真正的告警**。

## 三、逐步实现

### 步骤 1 · 准入：取消自动升

**落点**：`src/engine.ts` 的 `recordUse`（L1075-1102）

现状的核心（L1086-1101）：

```ts
const promote = normalized.status === 'approved'
  && block.quarantined !== true
  && block.injectedAuto !== false
  && (block.kind ?? 'fact') !== 'prompt'
  && !normalized.injected
  && hitCount >= AUTO_INJECT_HITS
const updated: StoredBlock = {
  ...block, hitCount, lastUsedAt: now,
  ...promote ? { injected: true, injectedAuto: true } : {},
}
await table.put(id, updated)
if (promote) this.ctx.emit('memory/changed', { operation: 'injected', id, injected: true })
```

**改法**：记账三件（`hitCount` / `lastUsedAt` / `put`）保留，`promote` 的赋值、展开项与 `emit` 一并去掉。函数的文档注释同步改写——它现在只做记账。

**常量改名**：`AUTO_INJECT_HITS`（L201）→ `CANDIDATE_HITS`，注释改为「体检报告列出候选的命中阈值」。值**暂不动**（保持 2）：取消自动升之后，阈值影响的只是报告的宽度，不再是状态的变更。

**候选的计算**（纯函数，放在 `engine.ts`；两个消费方——注入诊断行的一行提示，与体检报告的完整清单）：

```ts
/** 候选：被反复检索命中、但未被显式钉住、也没被人工否决过的记录。只提示，不改状态。 */
candidates(projectCwd?: string): MemoryRecord[] {
  // status === 'approved' && quarantined !== true && injected !== true
  // && injectedAuto !== false && (kind ?? 'fact') !== 'prompt' && hitCount >= CANDIDATE_HITS
}
```

条件与删除前的 `promote` **逐条对应**——这是刻意的：判据没变，变的只是它的作用（提示而非改状态）。

**历史数据**：`injectedAuto: true` 的记录**不改写**。`demoteStaleInner`（L1208-1230）保持原样——它只作用于 `injectedAuto === true`，取消自动升之后不再有新记录带上这个标记，这条规则自然只减不增。

### 步骤 2 · 在场：排序去掉检索记录

**落点**：`src/injection.ts` 的 `renderInjection`（L88-89）

```ts
// 现状
const ordered = [...records].sort((left, right) =>
  (right.lastUsedAt ?? right.updatedAt) - (left.lastUsedAt ?? left.updatedAt))

// 改后
const ordered = [...records].sort((left, right) => right.updatedAt - left.updatedAt)
```

函数注释（L79-81「按使用序降序」）与 `InjectionRender.lines` 的注释（L62「按更新时间降序」）同步订正。

**为什么这一行是本次最关键的一行**：`lastUsedAt` 由 `recordUse` 在**检索路径**上刷新，而检索是「需要时才用」的行为。排序一旦依赖它，「查得多的」就会挤掉「钉得牢的」，并且**一次 `memory_search` 当场改变下一轮的注入内容**。换成 `updatedAt` 之后，只有内容被修改（`remember` / `update`）才会影响次序。

**保留不动**：`omittedNotice`（L119-125）。取消自动升之后，所有常驻都是显式钉的，被挤出去的每一条都值得看一眼——这一行的语义从「噪音」升级为「告警」。

### 步骤 3 · 退场：失效表达

#### 3a. `path-exists` 锚点

**`src/anchors.ts`**

```ts
/** 受控词汇表：写入时只能从这四种里选，不能自创（自创的锚点无法机械校验）。 */
export type AnchorKind = 'env' | 'tool-list' | 'self-version' | 'path-exists'
```

`AnchorProbes` 加一个字段：

```ts
/** 会话工作区 cwd；`path-exists` 用它解析相对路径。缺省时相对路径判为「未校验」。 */
workspaceCwd?: string
```

**构造点**：`engine.ts` 的 `anchorProbes()`（L1011-1024）——它现在**没有形参**，而唯一的调用点在其上方：

```ts
// engine.ts:1000（在 runMaintenanceOnce 内）
const staled = await this.verifyAnchors(this.anchorProbes(), projectCwd)
```

所以签名要改成 `anchorProbes(workspaceCwd?: string): AnchorProbes`，调用处传 `projectCwd`。**启动维护的真实入口是 `runMaintenanceOnce`（L987）**，它的调用点在 `ensureProjectOpen`（L982 注释）——不是 `index.ts`。

`probeAnchor` 加 case：

```ts
case 'path-exists': {
  if (anchor.name === undefined || anchor.name === '') return undefined
  const relative = !isAbsolute(anchor.name)
  if (relative && (probes.workspaceCwd === undefined || probes.workspaceCwd === '')) return undefined
  const target = relative ? resolve(probes.workspaceCwd as string, anchor.name) : anchor.name
  return existsSync(target) ? 'present' : 'absent'
}
```

**取值域**：`'present'` / `'absent'`——写入时声明「这个路径（不）存在」。`anchorHolds` 不用改（它只做字符串比较）。

**顶注要订正的地方**：`anchors.ts` 开头写着「探测必须零 IO」。`path-exists` 需要一次 `existsSync`——这是**一次 stat，不是子进程**，在会话启动路径上可以接受；注释里把这条界线写清楚：**禁止的是 spawn，不是文件探测**。

**写入通道的坑**：`memory_save` 的 anchor 参数在 `src/index.ts` L330-333 声明，而 L352-354 有一个**硬编码的三元类型断言**：

```ts
{ anchor: args.anchor as { kind: 'env' | 'tool-list' | 'self-version', name?: string, value: string } }
```

两处都要改，否则运行时能写入、类型层面装作没有这个 kind。

#### 3b. `supersedes` / `retract`

**引擎侧**（`src/engine.ts` 新增两个方法，与 `update` 平级）：

```ts
/**
 * 语义作废：把 `targetId` 标成被 `id` 取代。
 * 走 locateRecord（跨链定位，与 0.10.0 一致），下游复用既有的 stale 行为
 * （撤常驻、不排除检索、带标注等核对回写）。
 */
async supersede(id: MemoryId, targetId: MemoryId, projectCwd?: string): Promise<{ updated: number }>

/** 撤回一条记忆：标 stale + 原因。内容保留（不删除）。 */
async retract(id: MemoryId, reason: string, projectCwd?: string): Promise<MemoryRecord>
```

写入形态：

```ts
{ stale: true, staleReason: `被 ${String(id).slice(0, 8)} 取代`, injected: false, injectedAuto: false }
{ stale: true, staleReason: `已撤回：${reason}`, injected: false, injectedAuto: false }
```

**为什么两个都撤常驻**：内容已作废，继续每轮注入就是误导——这正是 `verifyAnchorsInner`（L1262-1270）在锚点失效时的既有处置，语义一致。

**工具侧**（`src/index.ts` 的 `memory_update`，L574-595）加两个可选参数：

```ts
supersedes: { type: 'string', description: '把这个 id 指向的记忆标成「被本条取代」（本条内容不变，只写对方的作废标记）。省略则不动。' },
retract: { type: 'string', description: '撤回本条：给一个原因即标记作废（内容保留，不再注入，检索仍可检回）。省略则不动。' },
```

`execute` 里按参数分派：`supersedes` → `memory.supersede(id, args.supersedes, cwd)`；`retract` → `memory.retract(id, args.retract, cwd)`；两者都没给才走原来的 `update`。**三者互斥**，同时给两个时按 `retract` > `supersedes` > `update` 的次序取第一个，并在描述里写明。

**不新增工具**的理由：作废是「改一条记忆的状态」，与 `memory_update` 同属一个动作面；新开工具会让工具面继续膨胀（本环境工具面已是主要成本项）。

### 步骤 4 · 体检：只读报告

**引擎侧**新增：

```ts
export interface SweepReport {
  /** 当前 stale 的记录（含原因）。 */
  stale: Array<{ id: string, reason: string | undefined, summary: string }>
  /** 久未被检索命中的记录（`lastUsedAt ?? updatedAt` 早于阈值）。 */
  longUnused: Array<{ id: string, lastUsed: number, summary: string }>
  /** 候选（步骤 1）：被反复命中但未常驻。 */
  candidates: Array<{ id: string, hitCount: number, summary: string }>
  /** 常驻与预算：总数 / 预算 / 未注入数。 */
  resident: { total: number, budget: number | null, omitted: number }
}

/** 只读体检：不写任何状态（含不写时间戳）。 */
async sweep(projectCwd?: string, options?: { days?: number }): Promise<SweepReport>
```

**久未命中阈值**：`DEFAULT_SWEEP_DAYS = 90`，可由工具的 `days` 参数覆盖。**为什么是 90 而不是 30**：30 天是「自动升上来的常驻是否还有价值」的判据（撤常驻用），而久未命中的对象**本来就不是常驻**——非常驻的记忆几十天不用是常态，阈值定得太低会把正常记录报成待清理。

**体检的触发点**：`runMaintenanceOnce`（`engine.ts:987`）在 `verifyAnchors` 之后调一次 `sweep()`，结果存进实例字段 `this.lastSweep`（进程内，不落盘；每次会话首次打开工作区表时刷新一次）。

**注入侧**（`src/index.ts` 的 `recallText`，L208-227）加两种输出，都不占预算：**本次校验发现的新失效**（稀有，出现即值得看一眼），以及**候选提示一行**（数量 + 前 3 条摘要，长度恒定，不随候选数增长）。

```ts
// 校验结果由 verifyAnchors 写入引擎实例字段（进程内，不落盘）
const swept = memory.lastSweep
if (swept !== undefined && swept.stale.length > 0) {
  parts.push(`（本次校验发现 ${swept.stale.length} 条记忆失效：${...前 N 条摘要}）`)
}
```

**为什么只报这一种**：它是**稀有且必须立刻知道**的——一条记忆失效意味着「按它行动会出错」。久未命中与候选都是待办性质，随体检报告按需查看即可。

**新工具** `memory_sweep`：

```ts
name: 'memory_sweep',
description: '只读体检：列出失效的记录、久未被检索命中的记录、被反复命中但未常驻的候选，以及常驻与注入预算的占用情况。不修改任何状态。'
// 参数表留空：阈值用常量 DEFAULT_SWEEP_DAYS。工具参数里目前没有 number 类型
// 的先例（`index.ts` 的 `type: 'number'` 只出现在输出 schema RECORD_SCHEMA），
// 不拿一个未验证的参数类型去赌；要可按需覆盖时再加。
```

久未命中的阈值先写死为常量 `DEFAULT_SWEEP_DAYS = 90`。等真有「想按别的天数看一眼」的需求时再加参数——那时也顺便验证了 `defineTool` 的数值参数写法。

**这个工具的触发是什么**（不写清楚，实现时很容易把它做成一个没人读的机制）：

| 清单项 | 读者 | 到达方式 | 触发 |
|---|---|---|---|
| 候选 / 新失效 / 预算占用 | 模型 | 诊断行 | 每轮自动，不依赖调工具 |
| 久未命中 + 全量清单 | **模型** | 本工具 | 模型怀疑记忆出问题时；或用户提出疑问时 |

**读者是模型，不是人。** 本插件的原则是「记忆由系统与模型自行维护，人工只在例外时介入」——把人设成体检报告的常态读者，等于违背这条原则。人真正会介入的场景只有一个：**在对话里察觉到模型对某件事记得不对，于是提醒模型自检**。那时模型调本工具，把库里的实际状况列出来，这才是它的用途。

**「人提醒自检」时的工具分工**（值得写清楚，因为两个工具都会用到）：

| 步骤 | 用什么 | 看什么 |
|---|---|---|
| 先查「关于这件事我记了什么」 | `memory_search` | 命中记录的内容、`stale` 标注与 `staleReason` |
| 具体条目都没问题、但仍怀疑整体 | `memory_sweep` | 全库状况：有哪些失效、久未命中、候选、预算占用 |

也就是说 `memory_sweep` 在这个场景里是**次级入口**：先按主题查（`memory_search` 本来就带 `stale` 标注，`index.ts:79` 的字段描述写着「据此行动前先核对现状」），查不出问题时再看全局。**自检 ≠ 清点全库**，它是「针对这一件事，我的记录是否还成立」。

**因此它不需要定期读者，也不需要「每日一次」的守卫**：按需调用的工具，有人问它就活，没人问它不产生任何成本（不占预算、不落盘、不写状态）。这与 Aik358 那些「测了没人读」的机制的关键差别是——**那些机制假设存在定期读者**（定时器跑、结果落盘、做进看板），而这里不做这个假设。

**`GUIDANCE`**（L184 区域）补一句：库变大之后用 `memory_sweep` 定期体检，不要等注入诊断行堆积。

### 步骤 5 · 文案同步：三份行为控制器

**为什么单列一步**：`SELF_DESCRIPTION`（每轮注入的自述）与 `GUIDANCE`（`tool:memory` section）**不是说明文档，是模型行为的实际控制器**——0.9.2 的审计定过这条判据：陈旧等于行为错。0.12.0 推翻了两条自动规则中的一条、改了排序依据、多了一个工具，三处文案必须同步；否则模型会继续按一份已经不存在的机制行事，而它读起来毫无异常。

| 位置 | 现状 | 改成 |
|---|---|---|
| `src/self.ts` L35 | 「开关有两条自动规则：命中累计 2 次自动开启、30 天未命中自动撤下」 | 只剩一条：30 天未命中撤下**自动升上来的**常驻；命中不再改状态，只进候选提示 |
| `src/self.ts` L37 | 「按最近使用优先取舍」 | 「按最近更新优先取舍」 |
| `src/self.ts` L24 | 「你有 10 个工具」 | 11（加 `memory_sweep`）——0.10.0 曾因同类遗漏（漏列 `prompt_*` 系列）改过一次 |
| `src/index.ts` L185-186 / L189-191 | 「不受两条自动规则（promote on repeated hits / 反复命中自动开启…）影响」 | 只剩自动降级一条；显式钉的**仍然双向豁免**（降级侧行为不变） |
| `injected` 参数描述（`memory_save` 与 `memory_update` 各一处） | 「不再被自动升级或自动降级」 | 「不再被自动降级」——自动升级已不存在 |

**顺带**：`GUIDANCE` 补一句 `memory_sweep` 的用途（什么时候该体检），与新增工具配套。

**验收**：若 `test/` 中有断言这些文案的用例，同步更新；没有则以逐句比对为准（比对时以**新语义**为真值，不以旧文案为真值）。

### 步骤 6 · 时间：可见与可筛（2026-09-23 并入）

**诉求来自用户**：「给记忆标记时间」。0.12.0 原本只让时间**参与**判断（步骤 2 的排序键、步骤 4 的久未命中判据），**没让它可见**——而可见与可筛是另外两件事。

#### 6a. 时间可见（注入行）

**落点**：`src/injection.ts` 的 `injectionLine`（L55-59）

```ts
// 现状
const scope = record.scope === undefined ? '' : `@${record.scope}`
return `- [memory:${String(record.id).slice(0, 8)}:${record.namespace}${scope}] ${deriveSummary(...)}`

// 改后：日期固定在前、scope 固定在后——日期是数字、scope 是点号，顺序固定即无歧义
const date = formatDay(record.updatedAt)   // 'YYYY-MM-DD'
const scope = record.scope === undefined ? '' : `@${record.scope}`
return `- [memory:${String(record.id).slice(0, 8)}:${record.namespace}@${date}${scope}] ${deriveSummary(...)}`
```

**取哪个时间**：`updatedAt`——与步骤 2 的排序键**同一个字段**。显示与排序用同一个依据，不制造第二个「新」的定义。

**为什么是绝对日期而不是「18 天前」**：相对时间**每轮都在变**，会把注入副本变成每轮漂移的文本。`memory:recall` 本来就是动态 context（注入列表随排序变化），但不必要的漂移仍应避免——**减少变化的维度是廉价的稳定性**。

**代价（明说）**：每条 +11 字符（`@YYYY-MM-DD`），11 条约 120 字符，占 1500 预算的 8%——**大约挤掉一条记忆**。这是「精益求精」的实际价格。若实测不划算，可退到 `@MM-DD`（同年内无歧义）或调高 `injectionBudget`。

#### 6b. 时间可筛（`memory_list` 过滤）

**落点**：`src/index.ts` 的 `memory_list` 参数 + `src/engine.ts` 的 `list` 过滤链

```ts
after:  { type: 'string', description: '只返回此后更新过的记忆（`YYYY-MM-DD`，或相对形式 `7d` / `30d`）。' }
before: { type: 'string', description: '只返回此前更新过的记忆（同上）。' }
```

**为什么用 string 而不是 number**：工具参数里目前没有 number 类型的先例（`type: 'number'` 只出现在输出 schema `RECORD_SCHEMA`），不拿未验证的参数类型去赌；string 也天然容纳 `7d` 这种相对写法。

**实现分工**：解析在工具层（`'7d'` → `now - 7*86400_000`），**过滤在引擎 `list` 的过滤链里**（与 namespace / status / injected 同级）。这是**纯读取过滤**：不碰打分、不碰 `markUsed` 记账。

**为什么这一版不碰 `memory_search`**：给检索加时间过滤要动**候选集**——过滤发生在打分前还是后、被过滤掉的命中**还算不算「用过」**（关系到 `hitCount` 与候选提示），都要单独论证。浏览式筛选没有这些问题，先做它。

#### 6c. 验收

- 注入行含 `@YYYY-MM-DD`，且该日期等于该条 `updatedAt` 的日期；
- 与 scope 组合不歧义：`[memory:xxxxxxxx:project@2026-09-14@..]`；
- `memory_list(after: '7d')` 只返回 7 天内更新过的；`before` 同理；
- 预算用例：加日期后注入条数如实变化，且诊断行的「另有 N 条」同步。

**注入中和的逐字段投毒**（2026-09-23 借鉴 Aik358 的验证方法）

**变异演示**：把排序用例与准入用例接进 `scripts/mutate-check.mjs`（当前只覆盖注入中和那一条）。
