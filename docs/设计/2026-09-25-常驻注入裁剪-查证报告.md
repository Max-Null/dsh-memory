## 一、被查证的问题

> 现在的常驻记忆是有超出裁剪的机制的，但是对于被裁剪的记忆，既不会被常驻机制注入，也不会按非常驻
> 被检索后注入，那就相当于静默丢失了。

## 二、结论

**判断成立，但「静默」一词要打折扣**——不是没有信号，而是**信号还在、提示力已经没了**。

拆成三条：

1. **成立**：被预算裁掉的记录确实不进上下文，且**没有任何「因为被需要而回来」的路径**；
2. **成立**：它不会退回「非常驻」的待遇——没有这样一条待遇，非常驻记忆本来也不自动注入；
3. **补正**：每轮注入末尾有一行诊断（`（另有 N 条常驻因预算未注入：…）`），所以并非无声；
   但它已常态化，读起来像统计而非待办。

**实测比预想严重**：26 条常驻里 **15 条不在场（57.7%）**。

## 三、实测数据（2026-09-25，本工作区）

| 项 | 值 | 来源 |
|---|---:|---|
| 常驻总数 | 26 | `memory_list({ injected: true })` |
| 实际注入 | 11 | 会话注入列表逐条计数 |
| 被裁 | 15 | 诊断行「另有 15 条常驻因预算未注入」 |

预算 1500 字符，单条上限约 135（标记 28 + 摘要 80 + 开销 27）→ 约装 11 条。
11 + 15 = 26，与 `memory_list` 的返回条数精确吻合。

## 四、机制分析

### 4.1 排序只看 `updatedAt`

`renderInjection`（`injection.js:77`）：`sort((left, right) => right.updatedAt - left.updatedAt)`。

同文件 `:72-74` 的注释写明了 0.12.0 的决定：

> 起不再看 `lastUsedAt`：那是**检索**留下的痕迹，而检索是「需要时才用」的行为——拿它决定「谁每轮在场」，
> 等于让「查得多的」挤掉「钉得牢的」……**排序只该由内容本身的变更驱动。**

**推论**：一次 `memory_search` 命中一条被裁的记忆，**不会**让它下一轮排到前面。

### 4.2 没有轮转

`renderInjection` 是「按序贪心累加，超预算则 `continue`」（`:82-96`）。每轮从同一批记录重新渲染，
排序键不变 → **同一批永远在场、同一批永远被裁**。不存在公平队列或轮换。

### 4.3 复活路径只有两条

1. 该记录自己 `updatedAt` 变新（即内容被改写）；
2. 别的常驻被撤下（`injected=false`）或删除，腾出预算。

**没有第三条**——尤其没有「因为它被用到过，所以回来」。

### 4.4 结构性后果：越稳定的越容易被挤掉

`updatedAt` 是唯一排序键 → 长期不更新的记录排在最末尾。而**稳定的规则类记忆恰恰最不常更新**，
这与常驻判据（`052e413c`：按「失效可察觉性」钉住规则/委托/判据）的意图**方向相反**。

9-18 的设计文档在反例 2 里已经写过这句话，现在它在真实数据上兑现了：当前被裁的 15 条里，
包含铁律级的 `1c19d2f8`（DSH 源码只引用不改）、`d12d828b`（symlink 血的教训）、`8b20c9ba`（记忆层级委托）。

## 五、与 2026-09-18 设计的关系

那份设计**完整预见了**这个问题，且给出了明确的选择：

| 9-18 的判断 | 现在的现实 |
|---|---|
| 反例 1「以为在场，其实不在场……8 条常驻出局这件事没有任何人知道」 | 15 条出局；诊断行已存在 |
| 反例 2「越稳定的约定越容易被挤掉」 | 已兑现（见 §4.4） |
| 反例 3「清理没有触发点……只能靠人想起来清」 | **清理没有发生**——15 条积压 |
| §六.3「排序是否该引入重要度？倾向前者（把清理做干净比给排序加权重更简单）」 | 清理路径未被执行，问题回到原点 |

**实现与设计的一处偏离**：设计 §3.2 主张诊断行只给 id、不给摘要（上下文稀缺，id 够定位）；
实际实现带了 24 字符摘要，理由写在 `injection.js:100-101`：

> 带短摘要而不是只有 id——「主动去查这个 id 是什么」正是最容易省略的那一步，而省略它就等于看不出来。

这个偏离是**对的**（降低了下游动作成本），但它也说明当时已经意识到「看到了不等于会去查」。
现在的问题是同一件事的下一层：**看到了、也知道是什么，仍然没有去动它。**

**判据**：9-18 把问题定义为「看不见」，解法是「让它可见」；实测表明瓶颈不在可见性，
而在**看见之后缺一个理由去处理**。诊断行的文案「另有 N 条…」读起来像统计，不像待办。

## 六、附带发现：体检工具在数据缺失时不声明

同一会话实测：`memory_sweep` 返回

```json
{"resident": {"total": 2, "injected": 2, "budget": 1500, "omitted": 0}}
```

——**只统计到 global 的 2 条常驻，24 条 project 常驻完全不在报告里，而报告对此没有任何提示。**

**成因链**：

- `sweep()`（`engine.js:530`）先用 `await this.allRecords(undefined, projectCwd)`（`:536`），
  再用**同步只读缓存的** `this.recallRecords(projectCwd)`（`:550`）算 `resident`；
- `allRecords` → `projectChainTables` → `await this.projectTableFor(key).catch(() => undefined)`（`:425`）
  ——**打开失败被吞**；
- `recallRecords`（`:1561`）在表未打开时**静默退化为只返回 global**（`:1572`）；
- `memory_sweep` 的工具入口（`index.js:697`）是**唯一不调用 `ensureProjectOpen` 预热的工具**
  （对照 `:326` / `:345` / `:363`）。

本次的直接诱因是同一时段正在发生的 anchor schema 故障（project 表打不开）。**但缺陷独立于该诱因**：
任何导致表打不开的原因（存储损坏、并发句柄、版本不匹配、迁移失败）都会让体检报告变成一份
**看起来正常、实则缺一半数据**的报告。

**为什么它比裁剪本身更该先修**：讨论「要不要清理常驻」的前提是「知道有多少条常驻、几条出局」。
体检工具给出的数字残缺时，清理决策建立在错误前提上——本次就差点如此。

## 七、可选方向（供决策，非实现承诺）

| 方向 | 说明 | 代价 |
|---|---|---|
| **A. 提高预算** | 直接减少出局 | 与「防注入膨胀」的初衷相悖，只是把问题推后 |
| **B. 轮转 / 公平队列** | 出局者轮换上场 | 注入内容每轮变化，破坏提示缓存的稳定性 |
| **C. 重新引入检索信号** | 让 `lastUsedAt` 参与排序或复活 | 0.12.0 移除它的理由仍成立；需要区分「检索=需要」与「检索=查得多」 |
| **D. 重要度 / 优先级** | 9-18 §六.3 的未决项 | 必须先回答「谁定义重要度」 |
| **E. 分类配额** | 规则类与事实类各留预算 | 需要分类字段，是 D 的简化形式 |
| **F. 强化清理触发** | 把诊断行从「统计」改写成「待办」 | 成本最低，但仍是人工路径 |
| **G. 收缩判据纪律** | 承认「常驻 ≈ 11 条」是硬约束，钉之前先撤 | 不改机制，只改执行纪律（`052e413c` 已写明，实测未被执行） |

**倾向**：先 **G + F**（零机制改动，能立刻减少积压），再评估 B / E。**A 不建议**。

## 八、未决

1. **「被检索」该不该影响注入资格**：0.12.0 移除 `lastUsedAt` 的理由（避免「查得多的挤掉钉得牢的」）
   与现在「被需要的回不来」是同一机制的两面。若要重新引入，需要一条能区分二者的信号
   （例如：只让「被检索命中且**未常驻**」的进候选，已常驻的不参与排序）。
2. **被裁的 15 条该怎么分类**：其中有多少是「该撤下的过期约定」、多少是「被挤掉的规则」？
   这决定 G 能否解决问题，需要一次逐条清点（诊断行里的摘要够开始这项工作）。
3. **体检工具的完整性声明（§六）应当独立于本报告先修**——它影响的不只是常驻评估。
