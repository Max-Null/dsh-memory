# 静默记忆机制：设计方案（2026-09-15）

> 状态：**设计中**（第一版范围已定，待实施）
> 取代：`seek-soul-in-darkness/docs/设计/2026-09-01-记忆自动生效与后审核-改造计划.md`
> 关联：`docs/设计/DSH记忆插件-前置设计.md`（存储与检索的底子）、`CHANGELOG.md`

## 一、目标

把记忆做成一个**静默但有效**的插件：不需要用户逐条审核，也不需要用户判断哪条该常驻；长期使用后记忆库仍然新鲜、可用。

用户立场（2026-09-15）：**LLM 的事交给 LLM 自己处理，人不该介入**。对不了解 LLM 的用户，管理记忆这件事本身就超纲。人保留的只是**例外干预**（钉住、删除、回滚），而不是逐条放行。

## 二、设计依据：四个反例

设计的取舍都来自具体反例。记录它们是为了让后续改动能判断「是否推翻了当初的理由」——只有理由被推翻时，机制才该改。

### 反例 1：记忆越攒越多，却没人审

**动机。** 现有机制要求人逐条 `memory_confirm`、再逐个打开注入开关；现实是没人做，于是待审核条目堆积、审核与注入两个维度长期不动。

**→ 决定：默认自动生效。** 人的角色从「闸门」降为「例外干预」。

### 反例 2（DSH 0.1.5 → 0.1.6）：用得多 ≠ 还对

关于 DSH 0.1.5 版本特性的记忆，在内核升到 0.1.6 后成了错误信息，但它带着「DSH」这个标签、检索命中频繁。

- **推翻了什么**：「被检索命中 → 升常驻」的用进废退逻辑。命中只证明它被搜到，不证明它还对。
- **且无人取代它**：没有新记忆写进来，冲突检测永不触发。
- **→ 决定：引入有效性锚点。** 写入时声明它绑定哪个**可探测**的环境值（`env:dsh-version` 等，类型来自受控词汇表）；锚点不再成立即自动失效（撤注入 + 降权）。

### 反例 3（PowerShell 5.1 → 7.1）：没有更新的契机

环境事实类记忆（PowerShell 5.1 下的兼容性处理）在环境升级后静默失效，而插件根本不会被告知环境变了。

- **推翻了什么**：「检索时按需探测并标注」的写法——它把记忆的维护成本转嫁到模型的工作时间里：每次检索都要先核对，拖慢会话，让模型频繁陷入「校验记忆」而不是做事。
- **→ 决定：探测与比对移到会话启动时一次。** 环境变更几乎总伴随进程重启（升 PowerShell、换内核、改 PATH 都要重开会话），所以启动时校验天然够用；**检索路径只读状态、零探测、零比对**；失效提示**每条每会话至多一次**，且只对高频命中的少数条目提示，其余静默降权。
- **附加决定**：**不能核对的记忆不许常驻。** 无锚点的事实类留在按需检索里，把「无法预判的过时」推迟到「检索时用上下文判断」。

### 反例 4：标签有疏漏，一直没被检索到（或一直被错误检索）

关键词写得不全 → 该被找到的记忆永远找不到；写得泛 → 命中一堆无关条目。

- **推翻了什么**：「用进废退」能识别无用记忆。现有信号里，「该用却搜不到」与「真没用了」完全一样（都是 `lastUsedAt` 为空或很旧）——照此沉底会误杀。
- **且没有信号**：漏检不产生任何事件，无从复审。
- **→ 决定**：① 写入时 keywords 覆盖多角度（同义词、缩写、中英、领域词，以及「将来我会用什么词去找它」），由写入那一刻的模型产出；② **查询日志**——记录弱命中与空命中的查询，低频反查「这些查询本该命中谁」，命中就补 keywords；同一份日志反过来治误检（命中却从未被采纳的条目降权）。
- **语义检索的定位**：插件侧混合检索（记录持久化 vector、BM25 与语义结果 RRF 融合、缺配自动降级）**已实现**，但 `embeddings` 要宿主装配层提供 `embed` 实现，而 DSH 0.1.5-rc.2 **没有 embedding seam**（实测：源码里 `embedding` 命中的全是普通词义，唯一贴边的是 Exa 搜索自己的 neural 模式）。外部 API 会外发记忆内容，与隐私取向相冲 → **列为日后可选增强**，第一版不依赖它。

### 反例 5：迁移过来的机制会变成僵尸（dsh-habit / dsh-guardian 实证）

两个从 OpenCode 时代迁移的插件长期处于「实际废弃」状态，但形态不同：

- **dsh-habit**：`habit.json` 691 B，最后写入 2026-08-16（迁移当天），此后零新增——**数据停滞型**。
- **dsh-guardian**：`guardian.json` 46 KB，最后写入 2026-09-15，含 160+ 会话记录与 20 条待处理项——**空转型**：它一直在勤奋地写数据，但从会话的 system prompt 看，没有任何 guardian 内容进入注入，也就不改变任何决策。

**→ 决定（两条）：**

1. **不做「书记员」子 agent。** 曾考虑用一个子 agent（或一次 flash 调用）读会话内容、判断该不该更新记忆。放弃的理由：它唯一的不可替代价值是「质量纪律」，而那可以用注入文本承载；而它带来的成本（额外调用、额外机制、失败模式）与僵尸风险（见第 2 条）都不划算。改为**注入驱动**：像 genui 那样，把「何时该记、何时该更新、什么不该记」写进每轮注入的自述里，由主模型在会话中自觉执行。
2. **有效性按影响力衡量，不按活动量。** 一个每天写数据却不改变任何行为的插件，与完全停写的插件对使用者没有区别——而前者更容易骗过「它还在跑，应该没事」的检查。因此每条记忆记**来源**（主模型 / 人工），面板与查询日志按来源统计三个数：写入量、被检索命中数、被人工删除数；某个来源长期「写入多、命中 0、删除多」即是关闭信号。这条同时是 habit / guardian 去留的判据（见「未决」）。

## 三、机制设计

### 3.1 写入闸门（自动生效 + 硬拦）

- 危险内容（密钥/凭据正则）→ **隔离**：需要新增 `quarantined` 位，否则 `memory_search` 仍会把它交给模型（机制自述写明「待审核的记忆也可检索」）。
- 其余写入即 `approved`；`injected` 不给人开。
- keywords 按多角度产出（见反例 4）。

### 3.2 注入闸门（信号驱动升降）

- 升：命中计数达阈值且跨多个会话 → `injected = true`。
- 降：超过 T 未再命中 → `injected = false`（退出每轮付费，仍可检索）。
- 前提：新增**命中计数**——现在只有 `lastUsedAt` 时间戳，没有次数；只看「最近命中过」会被一次偶然命中触发。

### 3.3 退役（两段式，不新增状态）

- 第一段：撤注入（3.2 的降）；第二段：面板「冷组」默认折叠。
- **不新增 `archived` 状态**：面板已有 `isCold`（30 天未检索），把它从「提示」升级为「默认折叠的分组」就拿到九成收益，且零 schema 变更、零迁移。

### 3.4 新鲜度（锚点 + 启动校验 + 使用时刻回写）

- 锚点类型（受控词汇表，第一版三类）：`env:dsh-version`、`env:pwsh-version`、`env:tool-list`。探测方式随类型固定，值在写入时声明。
- **会话启动时**探测一次并缓存（可搭在现有的首轮预热 `ensureProjectOpen` 位置上，不引入新生命周期钩子）；批量比对，结论写进记录状态。
- 检索路径零成本；失效条目在结果里至多提示一次，提示文本是**可执行指引**（「据此行动前先核对现状；核对后 `memory_update` 修正或刷新锚点」）。
- 回写由模型完成——它刚核对过现实，手里就有新事实，不需要额外调度。

### 3.5 检索质量（查询日志）

- 记录：查询文本（有界保留）+ 命中数 + 是否被采纳。
- 低频反查：弱命中/空命中的查询 → 本该命中谁 → 补 keywords，或指出知识缺口（「这类知识你还没有」本身也是有用信息）。
- 反用：命中却从未被采纳 → 降权。

## 四、原则（从反例提炼，供后续改动判断是否推翻）

1. **维护成本归系统，模型只被邀请一次。** 插件自己探测、比对、降权、沉底；只在模型拥有信息优势的那一刻（刚对着现实核对过）请它回写。把「请你判断这条还对不对」当作常态提示，等于把系统该干的活推给推理。
2. **不能核对的记忆不许常驻。** 不确定性留在检索时解决。
3. **降权而非删除。** 撤注入、沉底都可逆；删除权只在人手里（`memory_forget`）。
4. **能查到的不记。** 版本特性、机制说明这类可读到的知识，存「去哪查」的指针而不是结论快照——指针不随版本失效。
5. **失效发生在「没被用到的路径」上。** 过时（没人用）、漏检（搜不到）、误匹配（词面骗过）都发生在使用路径之外，所以插件必须**自己观察自己**（锚点探测、查询日志、检索自评），不能让模型在推理时替它体检。
6. **有效性按影响力衡量，不按活动量。** 写得多不等于有用；要看写的东西有没有被检索命中、被采纳、被人保留。没有影响面的机制应当关闭，而不是留着「反正它在跑」。
7. **写入由注入指引驱动，不新增中间层。** 该记什么由主模型在会话中判断（它在场、信息最全），插件只负责把它记好、记得新鲜、记得不臃肿——不引入子 agent 或后台分析管道，避免再造一个僵尸层。

## 六、第一版范围（最小可验证集）

按依赖顺序：

1. `quarantined` 位：危险内容不进检索、不进注入。**（已完成）**
2. 写入默认批准：低危内容即 `approved`。**（已完成）**
3. **注入的行为指引**：把「何时该记、何时该更新、什么不该记、怎么写关键词」写进每轮自述——这是「不要书记员」之后写入质量的唯一载体。
4. 命中计数 + 信号驱动 `injected` 升降（淘汰机制的入口）。
5. 锚点三类 + 会话启动校验 + 每条每会话至多一次失效提示。
6. 查询日志（有界保留）+ 低频反查；按来源统计影响力（写入量 / 命中数 / 删除数）。
7. 面板：冷组折叠、隔离区、来源与影响力视图；角色从「审核队列」改为「审计台」（默认不看，例外干预：钉住 / 删除 / 回滚）。
8. 记忆**来源**字段（主模型 / 人工），随第 6 项一起落——越早记录，历史数据越可回溯归因。

## 七、未决

- 阈值取值：命中计数 N、跨会话 M、未命中 T（建议 N=2、M=2、T=30 天，与现有 `COLD_DAYS` 对齐）。
- 锚点探测失败时的语义：探测不到应按「未校验」处理，不能判为「失效」。
- 查询日志的保留条数与隐私边界：只存本地；文本是否脱敏路径与凭据，按已定的硬拦规则一并处理。
- **dsh-habit 与 dsh-guardian 的去留**：两者当前都不改变任何决策（一个是数据停滞型、一个是空转型）。先不动手，等第 6 项的来源与影响力统计落地后用数据判：有影响面则改造，无影响面则移除。判据不看它们各自的运行日志（那正是「它在跑」的错觉来源），只看有没有产出进入检索结果、注入或人工决策。

**与方案的偏离（已确认的取舍）**：查询日志落在 `$DSH_HOME/storages/query-log.json`，与 `memory.json` 同级，而非方案写的 `storages/memory/` 子目录——同一份存储的数据不该分居两处。锚点 kind 取名 `env` / `tool-list` / `self-version`，不复用方案里的 `dsh-version` / `pwsh-version`：锚点要能核对的是「这条记忆记的环境事实还成立吗」，而不是某个具体命令。来源统计暂不报「删除数」——`forget()` 是硬删除，要统计就得引入墓碑记录，第一版不值这个复杂度。

**已知缺口**（有意留下的，不是待办遗漏）：

1. **检索返回值不设上限**：BM25 对常见 2-gram 命中面极宽，一句查询在本机返回 81 条。记账已限前 5 名（见 CHANGELOG 0.7.0），但**返回值本身没有收敛**——模型一次拿到 81 条摘要，多半只看前几条，其余是纯噪声。收敛它要动 `search` 的契约（面板、`prompt_search` 共用），留到有实际观感再定。
2. **客户端 TS 无人校验**：`tsconfig.json` 不含 `src/client`（无 react 类型依赖），面板改动只靠运行时与人工看。本机量过：纳入后有 7 个既有类型错误，目前不做。
3. **`source: 'human'` 还没有真实入口**：面板写入路径尚未落地，当前只有 `remember()` 默认的 `'agent'`。字段先落是为了让历史可回溯，不是为了先有 UI。

工具与文案同步：`memory_save` / `memory_update` / `memory_confirm` / `memory_search` 四个工具描述、GUIDANCE、面板分组词（待审核 → 待放行）、ORGANIZE_PROMPT。

### 兼容旧记忆（2026-09-15 实测 + 迁移方案）

用户的提醒：**改动必须兼容已有记忆**。以下用本机真实数据核过（全局 30 条 + 工作区 62 条）：

| 检查项 | 实测 | 结论 |
|---|---|---|
| 新增字段是否可选 | `quarantined` / `hitCount` / `injectedAuto` / `anchor` / `stale` 全部 optional | 旧记录通过 schema 校验 |
| 旧 status 枚举 | 存储层仍保留 `auto` / `suggest`，`normalizeBlock` 读时迁移 | 兼容 |
| 真实分布 | 全局 approved 29 / suggested 1；工作区 approved 60 / suggested 2 | **3 条 suggested 会卡住** |
| `lastUsedAt` / `hitCount` | 28 条有 `lastUsedAt`，`hitCount` 全部缺失 | 命中计数要从零攒 |
| 旧 `injected: true` | 1 条，无 `injectedAuto` | 视为「人工开的」→ 不自动降级（保守且正确） |
| 降级兼容 | `blockSchema` 非 strict，zod 默认 strip 未知字段 | 旧版插件读新数据不报错 |

**两个真实缺口与迁移办法**：

1. **旧的 `suggested` 会永久卡住**——旧语义里它是「等审核」，新语义里 `suggested` 只剩「隔离」与「人工回退」两种含义，两者对不上：它既不会被注入，也没人去放行。迁移时**逐条过 `detectSensitive`**：安全则升 `approved`（写入即生效的语义），命中则标 `quarantined` 进隔离。**必须先检测再放行**——若历史条目里含密钥，直接放行等于让它开始进注入。
2. **28 条有使用记录却计数为零**——它们是可能被反复用过的老记忆，却要从零攒两次命中。迁移时若有 `lastUsedAt` 则回填 `hitCount = 1`（保守），再命中一次即可升常驻。
3. 旧 `injected: true` 且无 `injectedAuto` 的**一律不动**——那是人工决定，不该被自动降级。

**安全网**：迁移前把全局与工作区存储 json 备份为 `.bak-<日期>-migration`（沿用仓库现有 `.bak` 习惯）；迁移计数进日志与面板；逻辑幂等，重复运行不二次改动。

**实机验证发现并修掉的三个缺陷**（单测补在 `memory.spec.ts`，都会写进 CHANGELOG）：

1. **命中记账没有上限**：`rank()` 把 BM25 命中的**全部**候选交给记账，而 BM25 对常见 2-gram 给全库打分——本机一句「实机验证标记」命中 81 条。三次测试检索就把 61 条工作区 + 28 条全局记忆全升成常驻，注入预算当场被占满。改为只记前 `HIT_MARK_LIMIT = 5` 名（返回值不变）。
2. **人工关闭的开关会被系统重新打开**：`setInjected` 写 `injectedAuto: false` 表示「人工接管」，但 promote 条件没读它——人手动关掉的记忆下次命中又被升回常驻。降级侧本来就尊重人工决定，升级侧漏了，改为双向豁免。
3. **模板混进记忆检索**：`list()` 默认不按 `kind` 过滤，模板因此进了 `memory_search` 的候选池——既占返回条数，又被记命中、升成常驻，最后出现在注入预览里（`prompt-a64qv` 实测中招）。`rank()` 改为默认只搜 `fact`（显式传 `kind` 的 `prompt_search` 不受影响），`recallRecords()` 另加兜底过滤。

**污染数据的还原依据**：promote 的前置条件含 `!injected`，所以任何 `injectedAuto === true` 的记录在污染前必然是 `injected: false`——据此把两张表整体还原不会覆盖任何人工设置。全局表直接用迁移前备份恢复（迁移在重启后自动重跑）；工作区表无备份，按迁移规则手工还原为 `hitCount = 1`。

**回滚**：把 `.dsh-tmp/dsh-memory-backup-<时间戳>/` 整个拷回 `~/.dsh/profiles/ssid/node_modules/@max-null/dsh-memory` 即可。
