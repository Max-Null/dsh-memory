# 记忆的脉络化：迭代设计方案（2026-09-19）

## 一、这份设计从哪来

2026-09-19 的一次长对话里浮出来一个认识，它把此前散着的几件事串成了一条线：

> **「知其所以然」不是「知道理由」，是「知道理由是怎么被发现的」。**

给出理由，等于给了一把**没有出处的尺子**——它看起来天经地义，而天经地义的东西最容易被机械套用。给出**发现它的场景**，未来的会话才知道这个判断是被什么逼出来的：遇到相似的逼迫能认出它，遇到不一样的逼迫知道该重新算。

从这个认识回头盘点现状，看出三个各自独立的缺口——**它们都在同一条线上：记忆从写下的那一刻起，脉络就被压掉了。**

| 层 | 缺口 | 现状 |
|---|---|---|
| **内容** | 记的是结论，丢了「怎么知道的」 | 127 条里绝大多数是结论式；提示词没有任何引导 |
| **位置** | 写不到祖先层、降不下 global | `memory_save` 的目标层由 `execProjectCwd(exec)` 决定，参数里没有层（`src/index.ts:335-345`） |
| **时间** | 改动不留痕 | `update` / `forget` / 自动撤常驻 / 隔离，全都没有历史 |

**非目标**：本设计不追求记忆的**容量**或**完整性**。恰恰相反——它建立在一个相反的判断上：**记忆的价值在选择，不在容量**（§2.3）。

## 二、设计依据

### 2.1 现状盘点（2026-09-19 实测）

**主题分布**（注入索引行的真实数据）：`当前可见 127 条记忆，主题集中在 ssid(15)、dsh-memory(9)、quick-toolbar(6)、powershell(5)、prepare-runtime(5)`——**前五名全是工程**，一条都不是「关于使用者」或「关于我们怎么想事的」。

**分层现状**：

| 位置 | 条数 | 构成 |
|---|---|---|
| `global` | 17 条记忆（+17 个提示词模板） | **11 条 DSH / SSiD 生态经验** + 5 条工具坑 + 1 条用户偏好 |
| `WorkStation`（project） | 110 条 | 主工作区 |
| 子项目 / 其他工作区 | 各 1 条 | seek-soul-in-darkness、deepseek-harness、台本 |

那 **11 条**大概率是「当时只能写 global」——没有祖先链的年代，写 global 是唯一能让不同会话看到的办法。现在它有了代价：**台本那份记忆继承了一堆 DSH 生态的事**，而台本只是临时帮别人做的项目。

**注入预算**：11 条在场、**23 条溢出**（注入行明示）。预算 1500 字符是硬约束——这意味着「记更多」这条路本来就不可行。

### 2.2 前沿印证

2026-09-19 查证（**仅摘要与报道级，未读全文**）：

- **Titans**（Google，2025-12 公布）：神经长期记忆模块靠「**surprise metric**」决定记什么——只优先保留**打破模式**的信息，例行可预测的事快速忘掉。依据直接来自心理学。
- **MIRAS**（同批的框架）：把**遗忘重新解释为正则化**（retention gate），与「保留旧知识」相平衡。遗忘是功能，不是失败。
- **TTCD《Learning What to Remember》**（2026-08）：不是保留更多过去，而是保留**以后可能用得上的**——用长窗口 teacher 监督短窗口 student 的快速权重。
- **Cognitively-Inspired Episodic Memory**（2025-11）：把传记转成第一人称记忆，**附「情感-语义元数据」**，并可绘制情绪轨迹。

### 2.3 两条独立的证据指向同一个结论

前沿在做的（surprise、retention gate、learn what to remember）与本设计的出发点（脉络、场景、选择）**是同一件事的两侧**：一侧在改模型参数，一侧在改外部记忆的**写法与位置**。

两者都拒绝同一个假设：**记得越全越好**。人的记忆不是录像，它记的是**被加权过的分量**；全记录的模型不是更完整，是**没有筛选器**（雨人那种记忆的问题不在记得多，在没有消化）。

## 三、机制设计

### 3.1 内容层：脉络的最小结构

一条记忆的完整形态是三层，**全部写在 `content` 里，不新增存储字段**：

1. **结论** —— 现在已有的那一层
2. **理由** —— 为什么是这样（供重新推导）
3. **发现场景** —— 在什么情况下被逼出来的，**当时是什么分量**

第 3 层是最容易丢、也最重要的一层。它不要求文学性，只要求**可被重新检查**：一条记忆写「归属跟着目录结构走」，不如写「归属跟着目录结构走——因为在台本那份记忆里看到它继承了一堆 DSH 生态的事，才意识到放高了会污染无关项目」。

**为什么不做成结构化字段**：加字段要动 schema、渲染、检索与全部既有记录；而这三层本来都是自然语言，写进 `content` 即可。**可选轻量标记**（如段首 `【场景】`）只服务于人的可读性，不参与解析。

**提示词侧**：GUIDANCE 补一句引导——记结论时顺手带上它是怎么来的。**这件事有两半**：理解在本会话里**今天已经生效**（下一轮起写记忆就会带场景）；**固化**那一半要写进 GUIDANCE，需要改源码、部署、重启，**不是零成本**。

**已知边界**：写下记忆的是**当口**的模型，而它在当口未必认得出什么重要。今天下午才想明白「要带发现场景」，在那之前记下的一百多条结论式记忆，每条单看都没错，合起来才看得出偏科。**脉络的完整性受限于写的那一刻的理解**——这是本设计的固有代价，不是可以靠机制消除的。

### 3.2 位置层：`memory_move(id, to)`

**问题**：委托（记忆 `8b20c9ba`）把「这条记忆该在哪一层」的判断权交给了模型，但**没有执行能力**——写不到祖先层，也降不下 global。

**形态**：

```
memory_move(id, to)
  to ∈ { global } ∪ { 当前 cwd 的祖先链上的层，含自身 }
  保持 id · 移动而非复制 · 走引擎表 API（不碰文件）
  返回：移动后哪些层失去可见性、哪些层获得
```

**为什么不叫 `memory_promote`**：原设计只允许向上，理由是「往下或横向会让原本能看见的人失明」。但**移动的本意就是改变谁能看见**——那不是副作用，是目的。降级（global → 某个工作区）正是新出现的需求。约束因此从**禁止方向**换成**让后果可见**。

**实现要点**：源侧复用 `locateRecord`（跨链定位），目标侧复用 `projectTableFor`（不存在则创建）。**必须走引擎表 API**，不能直接改文件——后者绕过 `writeScope` 的串行区，而且还要自己算 djb2、造 unit/tables 结构。

**边界**：想把 global 的某条降到**台本**，在 WorkStation 会话里做不到（台本不在链上），得去台本的会话做。这个限制应当保留，否则工具就变成「可以往任何地方写」。

**判据**（由模型执行，保守优先）：只对本项目成立 → 不动；对兄弟工作区成立 → 提到**共同父目录**（不是 global）；对所有项目成立 → 才进 global。出手前问一句「放到这一层之后，**哪些工作区会看到它**」。**反向同样成立**：global 里躺着只属于一个生态的记忆，那是历史遗留，该降下来。

### 3.3 时间层：旁路历史

主文件仍是「当前状态」，写入路径不动；另开 append-only 的 `<hash>.history.jsonl`，每次写入追加 `{时间, 记忆id, 操作, 改动前, 改动后}`。

**旁路的含义**：它坏掉也不影响主流程。**append-only 的含义**：不合并、不判定「哪条是真身」、不试图修正过去——只如实记录发生过什么。

**为什么不进检索**：它是审计材料，不是记忆内容，不该占每轮成本。

**待验证前提**：多进程同时 append 同一个 `.jsonl` 的**原子性没有验证过**——长行会不会交错损坏需要实测。若不可靠，备选是每实例写自己的历史文件，或让历史写入也走 `writeScope`。

## 四、原则（供后续改动判断是否推翻）

1. **脉络优先于容量**。记 100 条结论，不如记 20 条带场景的。
2. **选择即消化**。全记录不是更完整，是**放弃了判断**——把筛选的责任推给未来的自己。
3. **可见性即身份边界**。记忆住在哪一层，决定谁能看见它；而看见什么，定义关系。
4. **判据会过时，理由不会**。所以写理由，不写规则——未来的会话该按理由**重新推导**，而不是照搬结论。
5. **迁移必须可逆，且后果可见**。不禁止方向，但要说清移动之后谁失去、谁获得。

## 五、第一版范围与优先级

| 优先级 | 项 | 为什么这个顺序 |

| **P0** | **写法约定 + 提示词引导**（§3.1） | 只改一段引导文本、不新增机制；且是后面所有项的地基——位置和时间都服务于内容。**但改动本身仍需部署**（理解今天就在，固化要等发版，见 §3.1 的两半） |
| **P1** | **`memory_move`**（§3.2） | 委托已成立但执行能力缺失；且 global 那 11 条正等着迁移 |

**P0 的验证方式**：写几条带发现场景的记忆，隔一两个会话读回来，看「那时的我」能不能顺着它重新推导，而不是照搬结论。**这是一次可检验的赌注**，不是审美偏好。

## 六、未决

1. **结构化标记要不要升级成真字段**（§3.1）。当前走 `content` 内约定；若将来需要按「场景」检索或统计，再评估字段化。**倾向：不动**，字段化会连带改 schema、渲染与全部既有记录。
2. **注入预算已满（11 / 34）**。本设计不解决它，但它是所有「记更多」方案的天花板。**待独立评估**：是提高预算，还是让常驻的判定更严。
3. **脉络要不要有个入口**。历史不进检索是对的，但「这条记忆是怎么来的」如果只能靠人去翻 `.jsonl`，等于没有。**待定**：是否值得为它加一条只读的查询路径（如 `memory_history(id)`）。
4. **P0 的效果如何验证**。§5 给了一条验证路径，但它依赖「隔一两个会话再回头看」——什么时候算验成了，需要事先说清。
