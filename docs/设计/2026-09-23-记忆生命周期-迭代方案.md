# 记忆的生命周期：迭代方案（2026-09-23）

> 状态：**设计已定，待实现**
> 关联：`src/injection.ts`（注入选择）、`src/engine.ts`（升降级、锚点校验）、`src/anchors.ts`
> 依据：本文件 §二；`seek-soul-in-darkness/docs/调研/2026-09-23-记忆新鲜度对照与借鉴.md`、`2026-09-23-注入成本实测-第一批.md`

## 一、目标

让**谁进这一轮的上下文**由判断决定，而不是由使用记录决定；并让**退场**第一次能被表达。

三段加一层：

1. **准入** —— 一条记忆凭什么成为常驻；
2. **在场** —— 常驻之间谁真的进得了上下文；
3. **退场** —— 一条记忆凭什么叫失效；
4. **体检** —— 定期把该退场的找出来给人看（只读报告）。

**非目标**（明确不做，理由随附）：

- **不自动删除或改写任何记忆内容**——与本插件「人是例外干预者」的原则冲突。
- **不引入 LLM 作为整理的判据**——它不可复现，而「整理」这种低频动作一旦误判，代价是内容丢失。
- **不做时间感知检索 / recency 权重 / 记忆日**——各自有独立的适用条件（见 §七）。
- **不做自动失效检测**——Aik358 把这件事写进了代码但**从未接线**（`note-status.js:178` 自述），这个信号值得听。
- **体检的界面不出这一版**——报告走注入诊断行与工具输出。面板是纯展示工作，与引擎逻辑分属两个领域，独立成版的风险小得多。

## 二、依据：四个事实

**事实一：失效只有一个来源。** 现有 `stale` 由锚点探测驱动（`env` / `tool-list` / `self-version`），而这些锚点**都绑在可机械探测的环境值**上（`src/anchors.ts`）。内容层面的失效——「这条被更好的结论取代了」「当时记错了」——**没有任何通路**，只能靠人/模型主动 `memory_update` 覆盖，而覆盖后**旧内容直接消失**（没有「被谁取代」的痕迹）。

**事实二：整理这件事在 Aik358 那有四处「算了但没人读」。** 配额 verdict（唯一调用点是看板快照）、evidence 的 freshness、技能 90 天归档时钟（**零调用的死代码**，而 README 仍在承诺）、自动 supersede 检测（未接线）。这些不是疏忽（作者记在 BUGLIST 里），但它们构成一组现成的反面教材：**测量本身有成本（采样、落盘、面板），只有在有消费者时才划算。**

**事实三：库只增不减。** 30 天规则撤的是**常驻**（`injected`），不是内容；没有归档层；没有定期整理。2026-09-23 普查时可见 184 条记录、56 条常驻，而注入预算约 11 席——**「常驻」这个状态在库变大之后，含义会从「每轮在场」退化成「有资格排队」**。

**事实四：注入的选择一直在拿「使用记录」当「该不该在场」的证据——而这两件事是反的。**

2026-09-23 对两个存储文件做了一次普查（`memory.json` 42 条 + `memory_project_3rf76j.json` 142 条），常驻 56 条的构成是：

- **49 条（87.5%）来自「自动升」**——`hitCount >= AUTO_INJECT_HITS`（`= 2`，`engine.ts:201`）即自动置 `injected: true, injectedAuto: true`（`engine.ts:1083-1098`）；
- 6 条是显式钉的（模型或人），1 条是 0.8.0 之前的遗留。

**自动升的判据是倒置的**：「被检索命中 2 次」度量的是**它被想起来了**；而常驻的语义是**它不能被忘**。能被检索命中的，恰恰是检索已经够用的那些——真正该常驻的（想不起来去查的）命中次数永远是 0，自动升在原理上就够不着它。数据支持这一点：49 条里多数是**事实 / 案例 / 交付记录**，抽样的 7 条里 4 条明显该留检索；而显式钉的那 6 条全部是规则 / 委托 / 判据 / 关系类。

**在场的选择同样如此**：注入按 `lastUsedAt ?? updatedAt` 降序贪心填 1500 字符预算（`injection.ts:88-89`；`DEFAULT_INJECTION_BUDGET = 1500`，约 11 席），而 `markUsed` 挂在检索路径上（`engine.ts:903` 的 `recordUse`）——**一次 `memory_search` 就刷新了命中条的 `lastUsedAt`，从而改变下一轮的注入内容**。「我查过什么」于是变成「我每轮看到什么」：越常查的越在场，越不查的越沉底，而规则类记忆恰恰是长期不查的那种。

**实证**：清理前，注入的 12 席里混着一批案例类；而两条铁律级约定（「DSH 源码只引用不改」「deepseek-harness 共享只读」）连同「读源码前先 git status」「工作区三库架构」等，长期在预算外排队。清掉 31 条自动升的记录（§八）之后，这几条当场进入注入列表——**没有改任何代码，只是把用「使用记录」选出来的那些移出了队列**。

## 三、机制设计

### 3.1 准入：取消自动升

**判据**见 §二事实四。自动升不是「不够严格」，而是**测错了东西**——把门槛从 2 抬到 5，只是把同一个错误挪个位置。所以这里改的是判据的**作用**，不是它的阈值。

**改动**：`hitCount` 继续记账（它对诊断有价值），但**不再触发状态变更**。原自动升路径（`engine.ts:1083-1098`）产出的不再是 `injected: true`，而是一条**候选提示**：命中次数较高、且未被显式钉住的记录，在注入诊断行里列出，由模型或人裁决要不要钉。

**为什么是提示而不是静默取消**：模型忘记显式钉是真实存在的风险（本插件的写入依赖模型自觉，见 `docs/决策/2026-09-23-记忆写入的主体-自记而非他记.md`）。提示保住了「这条被反复用到」这个信号，但把决定权留在判断者手里——与本插件「整理产出判断材料而非自动动作」的原则一致。

**既有数据的处置**：`injectedAuto: true` 的历史记录**不自动改写**（那是一次未经判断的批量状态变更）。既有自动降级规则（`AUTO_DEMOTE_DAYS = 30`，`engine.ts:1209-1224`）只作用于 `injectedAuto === true`；取消自动升之后不再有新记录带上这个标记，这条规则自然进入「只减不增」。

**代价**：常驻不再自动增长。这是明知的选择——已经证明增长本身来自一个错误的来源。补偿是候选提示与 §八 的盘点动作。

### 3.2 在场：排序去掉检索记录

**现状**：`injection.ts:88-89` 按 `lastUsedAt ?? updatedAt` 降序。`lastUsedAt` 是**检索**留下的痕迹，而检索是「需要时才用」的行为——拿它决定「谁每轮在场」，等于让「查得多的」挤掉「钉得牢的」。

**改动**：排序键改为 `updatedAt` 降序。理由：`updatedAt` 只在**内容变更**时刷新（`remember` / `update`），不受检索影响，语义稳定——「最近被修正过的优先」。

**准入收紧之后为什么仍需要这一步**：常驻数量接近预算时排序大多不起作用；但它是**超预算时的兜底次序**，必须与准入使用同一类判据（判断，而非使用记录）。

**诊断行**：`omittedNotice` 保留现状——它列出因预算未注入的常驻，是「钉了却不在场」的唯一信号。取消自动升之后，未注入的每一条都是显式钉的，这一行因此从噪音变成**真正的告警**。

### 3.3 退场：两条来源，一个字段

**判据：失效是一个维度、多种来源，不该每种来源各开一个字段。**

现在 `stale` + `staleReason` 已经在位，且下游行为完整（撤常驻、不排除检索、带标注等核对回写——`engine.ts:1235-1236` 注释与 `:1248-1277` 实现）。所以这一层只做**加来源**，不动下游。

**来源 A：锚点扩型（可机械探测的失效）**

现有三型之外，加一个能覆盖「记忆引用的东西不存在了」的类型：

- `path-exists`：绑一个**工作区相对路径**或绝对路径；路径不存在即失效。
- 判据：纯 `fs.existsSync`，零 IO 成本问题（会话启动路径上本来就在做锚点校验）。
- 用它标注的记忆长这样：「这个项目的配置在 `config/legacy.ts`」——文件删了，这条就该失效。

**为什么是它而不是别的**：它是**能机械验证**的（不引入判断），且和现有三型同构（都是「探测一个值，比对写入时的快照」）。检测不到时同样按「未校验」处理，不判失效。

**来源 B：语义作废（需要判断的失效）**

- 在 `memory_update` 上加两个可选参数，或新增一个工具动作：
  - `supersedes: <被取代的记忆 id>` → 把目标条目标成 `stale: true` + `staleReason: '被 <新记忆 id> 取代'`
  - `retract: true` → 标示「这条当时就错了，直接撤回」，`staleReason: '已撤回：<原因>'`
- **触发者只有两个：模型（工具）与人（面板）**。不做自动检测（依据见 §一非目标）。
- **下游一行不用改**：撤常驻、检索带标注等核对——这些行为已经在 `stale` 路径上跑着了。

**为什么这条值得做**：它把「覆盖」变成「取代」。现在 `memory_update` 改内容时旧内容**直接消失**；而「被取代」的痕迹有独立价值——检索时看到「这条已作废，原因是 X」，对被主动查的人来说是信息而不是干扰（这也是 Aik358 那条双判据的用意：注入侧挡下、检索侧放行带原因）。

### 3.4 体检：启动 sweep

**核心判断：整理动作搭在会话启动路径上，不新增定时器。**

理由：Aik358 用定时器是因为它要处理**无人值守**场景（夜间自动跑）。我们不是——**人来了才需要整理**。而会话启动路径上**已经在做锚点批量校验**（`verifyAnchors`，`engine.ts:1233` 注释明写「会话启动时调一次」），把整理挂在那里即可：

- 加一个「**每日一次**」守卫（记一个 `lastSweepAt`，同一日内不重复跑）；
- 复用同一次遍历（锚点校验本来就要遍历全表）；
- **不需要 `setInterval`，也没有「错过就没有补偿」的问题**——下一次会话自然补上。

**整理产出什么**（每一项都要有消费者）：

| 产出 | 消费者 | 为什么它不会是「算了不用」 |
|---|---|---|
| **新失效项**（本次锚点校验发现的） | 面板 + 注入诊断行 | 与现有 `stale` 路径共用，已有消费者 |
| **久未命中清单**（`lastUsedAt` 超过 N 天，且从未被检索命中） | 注入诊断行（本版）/ 面板（后续） | 人看到清单就会决定删/改/钉——决策是人做的，脚本只递材料 |
| **常驻超预算提示**（钉了常驻但排不进注入的条数） | 已有（`omittedNotice` 诊断行） | 已经在跑，整理只是复用 |

**关键：整理不产生任何写操作**（除了 `lastSweepAt` 这个时间戳）。它只读、只出报告。这样它的失效模式最多是「报告不准」，而不会误删内容。

### 3.5 归档：暂时不做

**判断：现在做归档没有收益。**

我们的「冷数据」在**语义上已经等价于归档**——不进注入、只在检索里。真要做归档，只有两种含义：

- **移到另一个目录**（文件系统归档）→ 正是 Aik358 那个坑：`archive/` 不在任何检索源，「保底」变成「文件还在但搜不回来」；
- **从检索源移除**（降权或排除）→ 那才是真归档，但**需要先有判据**（多久没命中算冷？），而判据需要数据——**那是「久未命中清单」跑一段时间之后才有的事**。

所以顺序是：**先出清单 → 攒一段时间的分布 → 再定归档判据**。现在定阈值是拍脑袋。

## 五、验证

**准入**

- 命中 N 次（N > `AUTO_INJECT_HITS`）后，该条 `injected` 仍为 `false`，且出现在候选提示里；
- 既有 `injectedAuto: true` 记录**不被改写**。

**在场**（本次的核心回归）

- **检索不改变注入顺序**：连续 `memory_search` 命中若干常驻条之后，下一轮注入列表与搜索前一致；
- **内容更新改变顺序**：`memory_update` 之后该条前移。

**退场**

- `path-exists` 锚点的探测（存在 / 不存在 / 探测不到→未校验）；
- `supersedes` 写入后目标条的 `stale` 与 `staleReason`；
- 装配级：作废后的目标条**仍能被 `memory_search` 检回**且带原因，**不再进 `memory:recall` 注入**。

**体检**

- sweep 每日一次（同一日内不重复跑）、只读（除 `lastSweepAt`）；
- 报告内容包含本次新失效项。

**负向验证**（仓库纪律）

- 逐项关掉新行为（自动升恢复、排序改回 `lastUsedAt`、报告永远为空），确认对应用例变红——这是「用例真的在测这条行为」的证据，而不是「改完还能绿」。

**变异演示**：新用例接进 `scripts/mutate-check.mjs` 的清单（当前只覆盖注入中和那一条）。

**不新增外部依赖**：`path-exists` 只用到 `node:fs`。

## 六、覆盖空白

- **`path-exists` 的探测时机**：会话启动时校验，会话过程中文件被删不会有即时反应——要即时只能加 watcher，那是另一个成本量级，本期不做。
- **久未命中清单的阈值未定**：写「超过 N 天」而没有 N——需要先跑一段 sweep 看分布。
- **候选提示的形式未定**：命中次数阈值（多少算「反复用到」）、放诊断行还是工具输出、是否一行多条——实现时定。
- **`supersedes` 的链式引用**：A 取代 B、B 又取代 C 时，`staleReason` 怎么写才不产生无限链——本期只写直接引用，渲染留给面板。
- **排序键换成 `updatedAt` 的副作用未评估**：长期未修订但极重要的约定会沉底。若实践中出现，说明需要**显式的优先级字段**，而不是再换一个隐式信号。

## 七、为什么其余四项不进这个迭代

- **时间感知检索**：**已并入 0.12.0**（2026-09-23 修正，见实现方案步骤 6）。原先这里写「我们的记忆没有日期标签，要做得先解决『哪些记忆带时间语义』」——**这条论证是错的**：没有的是**内容里的**日期标签，而 `createdAt` / `updatedAt` / `lastUsedAt` 是**结构化的时间**，一直都在，门槛比 Aik358 从 label 里抠日期低得多。剩下的是**recency 权重**（时间参与打分），仍不在此列，理由见下条。
- **recency 权重**：它只该是微小加成（Aik358 给 0.05），而**我们检索排序现在是纯 BM25**——加权重前要先有「新近确实该优先」的证据。
- **记忆日**：它解决的是「跨午夜工作不被劈成两天」，而我们现在**没有任何按日切分的东西**（没有日志、没有日报）。没有切分需求就没有日界问题。
- **归档**：见 §3.5。

**这四项的共同点：它们都还不是问题。** 先做生命周期与体检——它们是「库变大」这件事直接压出来的需求。

## 八、运营记录：一次性清理（2026-09-23）

**背景**：§二事实四的普查暴露 56 条常驻里 49 条来自自动升，其中多数是事实 / 案例 / 交付记录。

**动作**：按「失效可察觉性」逐条判定，对判定为「留检索」的 31 条执行 `memory_update(id, injected: false)`。

**为什么可以直接做而不等 §3.1**：显式给 `injected` 值会写入 `injectedAuto: false`（`engine.ts:1571`），此后**双向豁免两条自动规则**——清理是永久的，不会被「命中 2 次」重新升回来。

**结果**：常驻 56 → **25** 条（global 2 + project 23）。注入诊断行从「另有 44 条常驻因预算未注入」降到「另有 14 条」。

**判据**：留下的能改变行为（约定 / 纪律 / 委托 / 判据 / 架构决策），撤掉的能查到（事实 / 案例 / 交付记录 / 参考 / 已过时计划）。

**进场变化（清理的直接效果）**：6 条长期在预算外排队的记录回到注入列表，其中两条是铁律级约定（「DSH 源码只引用不改」、「deepseek-harness 共享只读」），另有「读源码前先 git status」「工作区三库架构」「隔离三件套验证方法」「dsh-skills 适配包约定」。

**未做**：不删除任何记录（`memory_forget` 未使用）——撤的只是常驻资格，内容仍留在检索里。
